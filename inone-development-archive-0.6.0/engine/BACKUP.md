# Резервные копии и восстановление InOne Backend

## Реализовано

- `scripts/backup-db.sh` создаёт PostgreSQL custom dump, SHA-256 sidecar и хранит последние `BACKUP_KEEP` копий (по умолчанию 14).
- Если задан `FILES_DIR`, скрипт дополнительно создаёт tar.gz файлового каталога и SHA-256 sidecar. База и файловый архив создаются отдельными операциями; это не атомарный snapshot между PostgreSQL и файловым хранилищем.
- `scripts/restore-db.sh` проверяет наличие и контрольную сумму каждого архива до восстановления, требует пустую целевую базу и (для файлового архива) пустой каталог назначения. Архив файлов предварительно проверяется на абсолютные/`..` пути, ссылки и специальные файлы; распаковка выполняется во временный каталог внутри целевого `FILES_DIR` до восстановления PostgreSQL; после успешного `pg_restore` файлы переносятся из staging в целевой каталог с откатом уже перенесённых элементов при ошибке (сам mountpoint не переименовывается).
- `scripts/verify-restore.mjs` сравнивает набор таблиц, количество строк в каждой таблице и версии миграций. Источник и цель обязаны быть разными базами; обе должны содержать непустую `public.schema_migrations`.
- `test/backup.test.js` проверяет восстановление и данные, повреждённый dump, политику хранения, отказ от проверки базы самой с собой и отказ от двух баз без истории миграций.
- `test/backup-files.test.js` проверяет полный backup/restore `FILES_DIR`, а также отказ от traversal-путей, символических ссылок и повреждённого gzip до изменения целевой БД.

SHA-256 sidecar защищает от случайного повреждения, но не подтверждает подлинность архива: злоумышленник, который может заменить dump, может заменить и checksum. Архивы содержат чувствительные данные и должны считаться незашифрованными, если оператор отдельно не настроил шифрование.

## Запуск

Ежедневная резервная копия базы:

```sh
DATABASE_URL='postgresql://…' BACKUP_DIR=/var/backups/inone BACKUP_KEEP=14 ./scripts/backup-db.sh
```

База вместе с файловым каталогом:

```sh
DATABASE_URL='postgresql://…' FILES_DIR=/var/lib/inone/files BACKUP_DIR=/var/backups/inone ./scripts/backup-db.sh
```

Восстановление базы в пустую целевую базу:

```sh
./scripts/restore-db.sh /var/backups/inone/inone-….dump 'postgresql://…/inone_drill'
node scripts/verify-restore.mjs 'postgresql://…/inone' 'postgresql://…/inone_drill'
```

Для восстановления файлов передайте архив и пустой каталог назначения:

```sh
./scripts/restore-db.sh /path/database.dump 'postgresql://…/inone_drill' /path/files.tar.gz /var/lib/inone/files-drill
```

## Проверка реального SMTP-провайдера

Локальные `test/mail-smtp.test.js` проверки подтверждают SMTP hand-off на тестовом сервере. Для проверки учётной записи реального SMTP-провайдера предусмотрена отдельная команда, которая отправляет одно тестовое письмо только на явно заданный адрес:

```sh
INONE_SMTP_HOST='smtp.example.com' \
INONE_SMTP_PORT=587 \
INONE_SMTP_REQUIRE_TLS=true \
INONE_SMTP_USER='…' \
INONE_SMTP_PASSWORD='…' \
INONE_SMTP_FROM='InOne <noreply@example.com>' \
INONE_SMTP_TEST_TO='your-test-mailbox@example.com' \
npm run test:mail:live
```

Секреты задаются в защищённом окружении сервера/CI, не в Git и не в переписке. Успех означает, что SMTP-сервер принял сообщение; это не доказывает доставку во входящие, отсутствие спама или прохождение SPF/DKIM/DMARC.

## Рекомендуемый график

- Ежедневно: backup в отдельный каталог с ограниченными правами доступа.
- Еженедельно: восстановление в отдельную пустую базу и сверка через `verify-restore.mjs`.
- После каждого изменения схемы или файлового хранения: контрольный restore drill.

RPO 24 часа — только целевой показатель при успешном ежедневном backup. RTO не подтверждён до учебного восстановления на объёме, сопоставимом с production.

## Открытые production-блокеры

1. **Внешнее хранение:** копии должны покидать сервер приложения и храниться в отдельном аккаунте/контуре.
2. **Шифрование:** dump и файловые архивы содержат персональные данные и должны шифроваться до передачи во внешнее хранилище; ключ — отдельно от архивов.
3. **WAL/PITR:** непрерывная архивация WAL и восстановление на момент времени пока не настроены.
4. **Минимальные полномочия:** выделенная роль backup с минимально необходимыми правами; тесты сейчас используют административное подключение.
5. **Согласованность файлов и БД:** backup DB и FILES_DIR выполняются неатомарно; нужен согласованный snapshot/maintenance protocol для production.
6. **Безопасная доставка и мониторинг:** удалённая копия, алерт о просроченном/неуспешном backup, проверка checksum и restore drill должны быть автоматизированы.
7. **Проверка файлового архива:** отдельные integration-тесты backup/restore для FILES_DIR и безопасного поведения на некорректных архивах ещё требуются.

8. **SMTP-провайдер:** добавлена opt-in команда `npm run test:mail:live`; реальный SMTP hand-off не подтверждён до запуска с credentials провайдера и отдельным тестовым адресом.

До закрытия этих пунктов резервное копирование нельзя считать production-ready, а SMTP нельзя считать проверенным на боевом провайдере.
