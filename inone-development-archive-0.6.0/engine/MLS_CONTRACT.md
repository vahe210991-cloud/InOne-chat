# Контракт сервера для MLS (служба доставки)

- **Версия:** 2
- **Обновлён:** 2026-11-26
- **Статус:** контракт MLS и личных диалогов Beta 1.0; реализация в работе, exact-SHA acceptance pending.

## 1. Роль сервера

Сервер — служба доставки (Delivery Service) и хранилище ключевых пакетов (KeyPackage). Он:
- не расшифровывает сообщения;
- не проверяет подписи MLS-объектов: это делают клиенты;
- хранит и выдаёт непрозрачные байты, применяет порядок, лимиты и права группы.

## 1.1. Личные диалоги Beta 1.0

- `POST /direct-chats/open` с телом `{"userId":"<peer user ID>"}` создаёт или открывает единственный личный диалог для неупорядоченной пары аккаунтов.
- Room ID генерирует сервер; direct room приватный, не привязан к организации и не использует групповые join requests или invite links.
- Получатель **не принимает и не отклоняет запрос на переписку**. Отправитель автоматически подготавливает MLS-группу, резервирует KeyPackage каждого активного устройства получателя и отправляет per-device Welcome через Add Commit.
- Статус `provisioning` обозначает только внутреннюю подготовку MLS. Он не является пользовательским запросом или ожиданием согласия. После принятия Add Commit сервер активирует direct conversation; сообщения передаются обычным MLS message route.
- Серверное членство получателя появляется только вместе с MLS Add Commit/Welcome. Прямое добавление строки в `room_members` запрещено.
- Повторный запрос с любой стороны возвращает тот же direct room. Третий аккаунт не может получить доступ к диалогу или добавить себя в его roster.
- До первого доставленного сообщения contact prompt отсутствует. Первое сообщение от пользователя, которого нет в контактах получателя, создаёт строку действий **Принять** / **Заблокировать** под именем отправителя в списке чатов. Принятие добавляет отправителя в контакты, блокировка запрещает дальнейшие личные сообщения в обе стороны; ни одно действие не задерживает уже доставленное сообщение.
- Claim endpoint не выдаёт частичный набор KeyPackage: для каждого активного устройства получателя должен существовать подходящий пакет. Иначе возвращается `409 device_key_package_unavailable` без расходования частичного набора; тот же `claimId` можно повторить после публикации недостающего пакета.

## 2. Ключевые пакеты (сделано)

- **Загрузка:** `POST /mls/key-packages` с телом `{"packages": [base64, ...]}`. За один запрос от 1 до 50 пакетов. Один пакет от 1 до 4096 байт. Не больше 100 неиспользованных пакетов на устройство; сверх лимита — 409.
- **Счётчик:** `GET /mls/key-packages/count` → `{"available": N}` для текущего устройства.
- **Выдача:** `GET /mls/key-packages/:userId` — по одному неиспользованному пакету на каждое устройство пользователя. Пакет помечается использованным в той же операции. Если пакетов нет, ответ — пустой список, а не ошибка. Лимит: 60 запросов в час на запрашивающий аккаунт (429).
- **Вход:** все маршруты только с входом (401 без него).
- **Связь:** пакет привязан к паре «пользователь — устройство».
- **Проверка:** 4 теста, в памяти и на PostgreSQL. Поломки: повторная выдача пакета и лимит неиспользованных — тесты падают.

## 3. Состояние группы и коммиты (план, следующий срез)

- Для каждой группы MLS сервер хранит номер эпохи и хэш последнего принятого коммита.
- Коммит принимается только если его эпоха на единицу больше текущей, а базовая эпоха совпадает. Проверка и запись — одна операция. Иначе ответ 409 «эпоха устарела»: клиент получает свежее состояние и повторяет.
- Из-за этого две одновременные фиксации не создают две ветки группы.
- Коммит и приветственные сообщения (Welcome) записываются вместе, атомарно.

## 4. Доставка (план)

- **Приветственные сообщения** новым участникам — через существующую доставку «устройство — устройство» (`PUT /sendToDevice/...`), адресат — устройство нового участника.
- **Коммиты и предложения** — события группы в порядке эпох. Клиенты читают их через синхронизацию.
- **Прикладные сообщения** группы — зашифрованные события группы (как `POST /rooms/:id/events`). Сервер не видит содержимого. Права на отправку и правку — как сейчас.

## 5. Удаление и выход (план)

- **Удаление участника** — коммит с предложением remove. Сервер проверяет право `remove_members` по правилам группы.
- **Выход** — собственный коммит с remove для себя.
- **Удалённое устройство** получает коммит и перестаёт получать события группы. Проверено на клиенте в эксперименте: удалённый не читает новые сообщения.

## 6. Коды ответа

| Код | Когда |
|---|---|
| 400 | неверный формат или размер |
| 401 | нет входа |
| 403 | нет права |
| 404 | группы нет или она приватна для постороннего |
| 409 | конфликт эпохи или лимит пакетов |
| 429 | превышен лимит запросов |

## 7. Не решено

- **Запасной пакет** (LastResort): что выдавать, когда обычные пакеты кончились.
- **Очистка пакетов** при отзыве устройства. Сейчас пакеты не удаляются.
- **Срок жизни пакетов** (lifetime): клиент проверяет, сервер пока не удаляет истёкшие.
- **Аудит контракта** — вместе с аудитом ts-mls.


## 8. Состав группы в коммите (сделано, 2026-11-01 10:08 UTC)

Коммит может объявлять изменения состава открытым текстом: `changes: { "adds": [userId, ...], "removes": [userId, ...] }`. Поле необязательно, по умолчанию изменений нет. Сервер проверяет объявленное по правилам комнаты до записи, а криптографию проверяют клиенты.

- **Удаление:** удалённый должен быть участником; владельца удалить нельзя (409); удалить себя может любой участник; удалить другого может владелец или тот, у кого есть право `remove_members`; администратора не удаляет другой администратор (403).
- **Добавление:** добавляющий должен быть владельцем или иметь право `invite_members` (403); добавляемый должен быть известным аккаунтом (400) и не участником (409); каждому добавленному нужно приветствие в `welcomes` (400).
- **Приветствия:** получатель должен быть участником группы после коммита (400). Приветствия неизвестным и посторонним не отправляются.
- **Атомарность:** изменения состава записываются в той же транзакции, что и коммит. Если коммит отклонён (эпоха), состав не меняется.
- **Уведомление:** после принятого коммита с изменениями участники комнаты получают уведомление об изменении.
- **Не решено:** передача владения (сейчас владелец не может выйти); проверка подписи коммита клиентами (эталонный клиент в движке ещё не сделан); установившийся режим с обновлениями ключей.

## 9. Передача владения (сделано, 2026-11-01 10:08 UTC)

`POST /rooms/:id/owner` с телом `{"userId": "..."}`. Передавать владение может только текущий владелец. Новым владельцем становится участник группы. Прежний владелец становится обычным участником без прав администратора. Новый владелец получает все права владельца, в том числе ведёт состав коммитами MLS. Выход владельца из группы возможен только после передачи владения.

## 10. Размеры сообщений (сделано, 2026-11-01 10:10 UTC)

- Приветствие: до 512 КБ (`MLS_WELCOME_MAX_BYTES`). Для 500 участников измерено до 111 КБ.
- Коммит: до 256 КБ (`MLS_COMMIT_MAX_BYTES`). Для 500 участников измерено около 41 КБ.
- Число приветствий в одном коммите: до 50. Число изменений состава в одном коммите: до 50 на каждый список.
- Подробности и ограничения измерений: `MLS_GROUP_SIZES.md`.

## 11. Сообщения группы (сделано, 2026-11-01 10:10 UTC)

`POST /mls/groups/:id/messages` с телом `{"message": "<base64 шифротекста MLS>", "kind": "text|sticker|gif", "forwarded": true|false}`. Сервер читает открытый заголовок PrivateMessage: версия 1, формат приватного сообщения, идентификатор группы (совпадает с комнатой), эпоха (совпадает с текущей). Шифротекст сервер не расшифровывает. Лимит 64 КБ.

- `POST /rooms/:id/events` для групп с эпохой отвечает 409: сообщения только через новый маршрут.
- Правка сообщения группы MLS (`/edit`) отвечает 409 до появления контракта правки с проверкой эпохи.
- Удаление (`/redact`) не менялось.

## 12. Типы комнат и названия (сделано, 2026-11-01 10:11 UTC)

- `POST /rooms` с `kind` (`group` или `channel`) и `name` (1–64 символа). Канал без названия — 400. Название канала уникально среди каналов (без учёта регистра и лишних пробелов): занятое — 409.
- `PUT /rooms/:id/name` — владелец меняет название. Для канала проверка уникальности; для группы название может повторяться.
- `POST /rooms/:id/events` — 409 для всех комнат: сообщения только через `/mls/groups/:id/messages`.
- `POST /rooms/:id/events/:eventId/edit` — 409 для всех комнат до появления контракта правки с проверкой эпохи.
- `POST /rooms/:id/events/:eventId/redact` — без изменений.

## 12. Типы комнат и названия (сделано, 2026-11-01 10:11 UTC)

- `POST /rooms` с `kind` (`group` или `channel`) и `name` (1–64 символа). Канал без названия — 400. Название канала уникально среди каналов (без учёта регистра и лишних пробелов): занятое — 409.
- `PUT /rooms/:id/name` — владелец меняет название. Для канала проверка уникальности; для группы название может повторяться.
- `POST /rooms/:id/events` — 409 для всех комнат: сообщения только через `/mls/groups/:id/messages`.
- `POST /rooms/:id/events/:eventId/edit` — 409 для всех комнат до появления контракта правки с проверкой эпохи.
- `POST /rooms/:id/events/:eventId/redact` — без изменений.

## 13. Правка сообщения группы MLS (сделано, 2026-11-01 14:33 UTC)

`POST /rooms/:id/events/:eventId/edit` с телом `{"type": "m.room.encrypted", "message": "<base64 шифротекста MLS>"}`. Сервер проверяет автора, право `edit_own_messages`, окно 24 часа, группу и эпоху в открытом заголовке. Устаревшая эпоха — 409 с текущей эпохой. Правка — событие `m.room.encrypted.replace` с полем `payload.mls`.

## 14. Резервный ключевой пакет (сделано, 2026-11-01 14:34 UTC)

`POST /mls/key-packages/last-resort` с телом `{"package": "<base64 KeyPackage>"}` — один пакет на устройство, новая загрузка заменяет прежний. `GET /mls/key-packages/:userId`: сначала выдаётся обычный пакет (он расходуется); если обычных у устройства нет, выдаётся резервный (он не расходуется). `GET /mls/key-packages/count` резервный не учитывает.

## 15. Доставка участнику без связи (проверено, 2026-11-01 14:35 UTC)

Сообщения группы приходят через `GET /rooms/:id/events` (в открытом заголовке каждого сообщения видна эпоха), коммиты — через `GET /mls/groups/:id/commits?since=<эпоха>`. Клиент, который был без связи, идёт по эпохам: читает сообщения эпохи N, затем применяет коммит N -> N+1 и переходит к следующей эпохе.

## 20. Идентификатор сообщения клиента (сделано, 2026-11-01 14:38 UTC)

`POST /mls/groups/:id/messages` принимает поле `clientMessageId` (1–64 символа: буквы, цифры, `_`, `-`). Повтор с тем же идентификатором от того же пользователя в той же комнате возвращает первое сообщение (`event_id` тот же) и не создаёт второго. Без поля поведение прежнее. Неверный идентификатор — 400. Это защита от дублей при повторе отправки после потери ответа: клиент повторяет с тем же идентификатором.

## 21. Резервирование повтора (сделано, 2026-11-01 14:38 UTC)

Одинаковые запросы с одним `clientMessageId`, пришедшие одновременно, не создают дубля: одну строку вставляет только один запрос. Остальные получают `200` с тем же `event_id`, если первый уже записал сообщение, либо `409` («сообщение уже отправляется, повторите позже»), если запись ещё идёт. Если запись события не удалась, резервирование снимается. Проверено на PostgreSQL: без резервирования гонка воспроизводится, с резервированием — нет.


## 22. Сессии (сделано, 2026-10-30 06:52 UTC)

- `POST /login` и подтверждение нового устройства (`/approvals/:id/claim`) выдают `token` (токен доступа, 15 минут), `refreshToken` (одноразовый, 30 дней), `expiresAt`, `refreshExpiresAt`.
- Истёкший токен доступа: `401` с `code: "token_expired"`. Клиент обновляет его и повторяет запрос.
- `POST /token/refresh` с `refreshToken`: выдаёт новую пару, старый токен обновления гасится. Коды: `refresh_reused` (повтор: сессия устройства отзывается целиком, событие пишется в журнал), `refresh_expired`, `refresh_unknown`, `401 device_revoked` (устройство отозвано).
- `POST /logout`: завершает сессию устройства; устройство остаётся зарегистрированным.
- Восстановление аккаунта применяется раньше выдачи новой пары: отключённое устройство не получает токен.

## 23. Реализация и сверка с исходным кодом (2026-11-11)

Этот раздел имеет приоритет над более ранними формулировками «план» в разделах 3–7 и уточняет старые упоминания отправки через `POST /rooms/:id/events`.

В актуальном `src/server.js` реализованы следующие маршруты:

| Операция | Маршрут | Назначение |
|---|---|---|
| Отправка MLS-сообщения | `POST /mls/groups/:id/messages` | Проверка участника, capability, заголовка MLS, группы, эпохи, размера и clientMessageId |
| История комнаты | `GET /rooms/:id/events` | Выдача событий после joinedSeq пользователя |
| Чтение коммитов | `GET /mls/groups/:id/commits?since=N` | Получение коммитов в порядке эпох |
| Текущая эпоха | `GET /mls/groups/:id/epoch` | Состояние MLS-группы для участника |
| Получение Welcome | `GET /mls/welcomes` | Ожидающие приветствия для устройств пользователя |
| Подтверждение Welcome | `POST /mls/welcomes/:id/ack` | Подтверждение получения Welcome конкретным устройством |
| Загрузка KeyPackage | `POST /mls/key-packages` | Публикация обычных пакетов |
| Счётчик KeyPackage | `GET /mls/key-packages/count` | Число доступных обычных пакетов |
| Last-resort KeyPackage | `POST /mls/key-packages/last-resort` | Замена резервного пакета устройства |
| Claim KeyPackage | `POST /mls/key-packages/:userId/claim` и reservation-вариант `POST /mls/key-packages/:userId/claims` | Атомарное резервирование пакетов |
| Освобождение claim | `DELETE /mls/key-packages/claims/:claimId` | Освобождение резерва текущего устройства |
| Ожидающие удаления | `GET /mls/removals` | Состояние удаления устройств/участников |

### Обязательные ограничения клиента

- `POST /rooms/:id/events` не является маршрутом отправки. Для него возвращается HTTP 409 с указанием MLS endpoint.
- Сообщение отправляется только как base64 MLS ciphertext; сервер не должен получать plaintext.
- Повтор после потери ответа должен использовать тот же `clientMessageId`.
- При HTTP 409 `epoch_outdated` клиент обязан получить актуальные коммиты/эпоху и повторить MLS-операцию корректно, а не переслать старый ciphertext.
- История комнаты и коммиты должны синхронизироваться с учётом порядка эпох. Нельзя применять сообщения более новой эпохи до соответствующего коммита.
- WebView не владеет MLS-состоянием, секретами, refresh token или ключевым материалом. Это ответственность native MLS runtime (Stage 4).
