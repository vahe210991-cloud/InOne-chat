# Выбор мобильной библиотеки MLS: исследование

- **Составлено:** 2026-11-01 14:33 UTC (Ереван UTC+4).
- **Вопрос:** какую библиотеку MLS (RFC 9420) брать для мобильного клиента InOne (iOS и Android), чтобы она работала с нашим сервером и набором шифров `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- **Что проверено:** лицензии, аудит, мобильные привязки, активность, набор шифров. Источники: поиск по открытым страницам репозиториев, пакетных реестров и публикаций. Проверка на устройствах не проводилась.

## Кандидаты

| Библиотека | Язык ядра | Лицензия | Аудит | Мобильные привязки | Замечания |
|---|---|---|---|---|---|
| OpenMLS | Rust | MIT | SRLabs, 8 замечаний, одно высокой важности; низкое в работе на момент отчёта | Нет официальных; CI собирает aarch64 для Android и iOS, но не тестирует | Ядро для мессенджера Phoenix Air. Набор шифров из RFC обязательный (MTI) совпадает с нашим |
| OpenMLS, Dart-обёртка `openmls` | Dart + Rust | MIT | Не проверено | Есть: Android SDK 24+, iOS 13+ | Обёртка чужая: опубликована непроверенным загрузчиком, оценка здоровья 51/100 у агрегатора зависимостей, мало загрузок. Подходит только если клиент на Flutter |
| AWS mls-rs | Rust | Apache-2.0 или MIT | Полного аудита нет (указано прямо) | Не заявлены; нужны свои привязки | Заявлена полная совместимость с RFC 9420; наборы шифров 1,2,3,5,7 (включая наш) |
| Wire core-crypto | Rust | GPL-3.0 (по метаданным сборки) | Не проверено | Есть: Swift (iOS) и Kotlin (Android), зашифрованное хранилище | Копилефт: для закрытого коммерческого приложения нужны условия, которых в материалах не видно |
| Cisco MLS++ | C++ | Не проверено (в материалах не найдено) | Не проверено | Не найдено в материалах | Нужны собственные привязки на JNI и Objective-C++ |

## Вывод по данным

1. **OpenMLS** — лучший по соответствию: MIT, есть аудит, набор шифров наш, активная поддержка. Риск: мобильные сборки не тестируются в его CI, их надо проверить на устройствах.
2. **Свои привязки к OpenMLS** (UniFFI для Swift и Kotlin) надёжнее, чем сторонняя Dart-обёртка с низкой оценкой здоровья. Если клиент на Flutter, обёртку можно взять как образец, но не как зависимость.
3. **Wire core-crypto** — самый готовый для мобильных приложений, но GPL-3.0 мешает закрытому продукту без отдельной лицензии.
4. **mls-rs** — без аудита, мобильных привязок нет: сопоставим с OpenMLS по работе, но уступает по проверке.
5. **MLS++** — не рассматриваем без данных о лицензии и мобильных привязках.

## Что не проверено

- Реальная сборка и работа на устройствах (iOS, Android).
- Совместимость с нашим сервером и с ts-mls: нужна проверка обменом коммитами и сообщениями между OpenMLS и ts-mls на одном наборе шифров.
- Размер библиотек в мобильных сборках и время операций на телефоне.
- Актуальные версии: версии менялись быстро, фиксировать точные версии перед внедрением.

## Ответы владельца (2026-11-01 14:33 UTC)

1. **Клиент на Flutter, один код для всех платформ.** Мобильная криптография подключается через Rust-ядро и мост Flutter к Rust (flutter_rust_bridge). Привязки Swift и Kotlin, которые даёт Wire core-crypto, для Flutter напрямую не годятся: для каждой платформы понадобились бы свои каналы связи между Dart и нативным кодом. Поэтому для Flutter предпочтительнее OpenMLS, у которого Rust-ядро подключается одним мостом.
2. **Открытый ли код клиента — вопрос открыт.** Пояснение:
   - **MIT и Apache-2.0** разрешают использовать библиотеку в закрытом приложении; нужно сохранить уведомления об авторстве.
   - **GPL-3.0** (копилефт): если приложение содержит GPL-код и распространяется (App Store, Google Play, скачивание), весь код приложения должен быть выпущен под GPL с исходниками. Закрытый клиент с GPL-библиотекой невозможен.
   - **Коммерческая лицензия** — та же библиотека по второй лицензии, которая разрешает закрытое использование, обычно платная. Условия Wire в материалах не найдены, их надо запрашивать у Wire.
   - **Важно:** лицензия GPL-3.0 у Wire core-crypto указана в метаданных сборки; точный текст в файле LICENSE репозитория надо проверить.
   - Многие разработчики считают GPL несовместимой с правилами App Store, поэтому GPL-библиотека в закрытом приложении из магазина — риск даже при готовой открытой части.

## Варианты

| Вариант | Библиотека | Что получаем | Что теряем |
|---|---|---|---|
| Закрытый клиент | OpenMLS (MIT) | Никаких ограничений на код и магазины | Доверие к коду — опирается на аудит и открытое ядро |
| Открытый клиент | OpenMLS или Wire (GPL) | Доверие сообщества, возможность аудита кода клиента | Весь код клиента под GPL |
| Закрытый клиент | Wire по коммерческой лицензии | Готовые привязки (но для Flutter нужны каналы) | Стоимость и условия Wire, неизвестны |

Рекомендация: OpenMLS (MIT) — работает и для закрытого, и для открытого клиента, без юридических ограничений.

## Закрытый клиент: затраты (2026-11-01 14:33 UTC)

- **Предварительно:** владелец склоняется к закрытому исходному коду клиента InOne, при условии что это не добавляет затрат разработки.
- **Затраты разработки при OpenMLS (MIT):** нет. Работа та же, что для открытого клиента: мост Flutter к Rust и привязка ядра.
- **Затраты при Wire (GPL-3.0) в закрытом клиенте:** коммерческая лицензия, стоимость неизвестна, условия не найдены.
- **Работа, которая нужна в любом случае (не из-за закрытости):**
  - проверка лицензий всех зависимостей клиента, включая Flutter-пакеты и Rust-крейты;
  - экран с уведомлениями о сторонних компонентах: MIT требует сохранить уведомление об авторстве и текст лицензии;
  - внешний аудит клиента и криптографической интеграции: для мессенджера с шифрованием он нужен и для открытого клиента.
- **Что закрытость меняет:** доверие пользователей опирается на аудиты и описание протокола, а не на чтение кода сообществом. Сообщения по-прежнему зашифрованы, сервер их не читает.
- **Обратимость:** закрытый клиент можно открыть позже (MIT это позволяет); опубликованную открытую версию закрыть нельзя.
