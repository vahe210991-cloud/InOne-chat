## 3. Confirmed findings

### 3.1 File-download URLs are not device-bound or revocable

In the current Flutter branch's canonical backend:

- `GET /files/:id/url` authenticates the caller and checks current room membership/file ownership before issuing a URL.
- The signed download capability is an HMAC over `GET|fileId|expires`; the current TTL is five minutes.
- `GET /objects/:id` validates the signature, expiry and ready status, then returns object bytes. It does not re-authenticate the device or re-check current room membership.
- PostgreSQL `revokeDeviceInTransaction` removes device tokens, refresh tokens, keys, inbox/push/signing records and pending MLS material, but it does not invalidate already-issued object URLs or delete the file object.
- The existing `files.test.js` suite has no regression proving that a previously issued download URL stops working after device revocation or membership removal.

**Status:** confirmed source-level security gap. A copied URL remains a bearer capability until its five-minute expiry, even if the issuing device is revoked or room membership changes. Whether five minutes is an accepted revocation window is not specified in the owner requirements. Do not silently accept it as immediate revocation.

**Required fix:** add a revocable, device-bound download grant or route downloads through authenticated authorization on every request; define the required revocation latency; add PostgreSQL and memory regression tests for device revoke, room-member removal, URL replay and expiry. Keep URL tokens and file keys out of logs.

### 3.2 Encrypted attachments are not implemented end-to-end

- The backend object store persists the bytes it receives; it does not encrypt attachment payloads.
- The object-store comment assumes the client encrypts before upload, but the active mobile app does not yet provide the native MLS attachment encrypt/decrypt path.
- Stage 4's persistent Rust client/bridge exposes text messaging, not a complete attachment crypto/upload/download API.
- Sending an MLS message containing a `fileId` does not encrypt the file bytes.

**Status:** BLOCKED, not E2EE. Required implementation remains client-side authenticated encryption before upload, ciphertext-only object storage, encrypted manifest/key delivery inside an MLS application message, authorized download, local decryption and integrity/room binding tests.

### 3.3 Recovery deep link and verified-phone delivery remain blocked

The Stage 4 audit confirms the active Flutter app has no recovery-confirm route, no `app_links` initial/warm-link handler and no `confirmRecoveryLink` session method. The backend recovery contract exists, but production config currently rejects enabling SMS/required-phone while no real SMS provider is integrated.

**Status:** BLOCKED. Do not mark verified-phone recovery ready until the app-link host/platform association and real SMS delivery are configured and tested.
