## 0. Обязательное принятие правил

В начале каждой новой сессии:
1. Открой этот файл из актуальной ветки GitHub и прочитай его полностью.
2. Прочитай корневой `AGENTS.md`, `.github/copilot-instructions.md` (если работаешь через Copilot), `development/README.md`, `development/WORKING-RULES.md`, `development/HANDOVER-CHECKLIST.md`, последний baseline, последние отчёты и `docs/continuity/README.md` с документами, на которые он ссылается.
3. Найди самый новый отчёт и последнюю запись журнала. Не начинай с пересказа из памяти чата.
4. В первом сообщении владельцу кратко подтверди: прочитаны ли все обязательные документы; какой branch/SHA проверен; какие пять ближайших задач; какие ограничения или противоречия обнаружены.

Эта инструкция является обязательным проектным правилом. **Не утверждай, что она автоматически записана во внутреннюю память, системные навыки или настройки любой модели.** У разных моделей и чатов нет гарантированного общего доступа к памяти и навыкам. Долговременное сохранение обеспечивается файлами и историей GitHub. Если платформа поддерживает project-level instructions/skills, подключи или процитируй этот документ в рамках доступных возможностей, но не заменяй им файл в репозитории. Каждая новая сессия обязана заново читать актуальную версию из GitHub.

## 1. GitHub — единственное постоянное хранилище проекта

1. Единственная авторитетная копия кода, дизайна, документов, решений, бандлов, отчётов, тестовых результатов и истории — репозиторий GitHub `vahe210991-cloud/InOne-chat`.
2. Не хранить единственные или долговременные копии у себя: в локальной папке, личном облаке, временном хранилище модели, переписке, памяти чата, песочнице или незакоммиченном workspace.
3. Временная рабочая копия допустима только как технический этап обработки в текущей сессии. Она не является результатом и не должна быть единственным местом хранения. Все необходимые изменения должны быть закоммичены и отправлены в GitHub до завершения сессии. Если инструмент не позволяет выполнить push/commit, немедленно зафиксируй точный блокер в GitHub доступным способом либо сообщи владельцу, что handoff не завершён. Не заявляй о сохранении без проверенной ссылки.
4. Не удаляй и не перезаписывай исходные артефакты. Сохраняй provenance, имя, дату получения, checksum, версию, исходную ветку и историю.
5. Не коммить секреты, токены, приватные ключи, реальные коды подтверждения, персональные данные и production credentials.

## 2. Каждый файл, полученный в чате, должен попасть в проект

Это одно из главных правил.

Для каждого файла, архива, изображения, документа, кода, таблицы, лога, патча или иного вложения, полученного от владельца в чате:
1. Найди и проверь доступный файл. Не игнорируй вложение и не ограничивайся ответом по тексту.
2. Определи тип, назначение, версию, дату, содержимое, зависимости и целевую часть проекта.
3. Для архивов — перечисли содержимое, проверь структуру, выяви вложенные архивы и дубликаты; не распаковывай вслепую поверх существующих файлов.
4. Сравни с текущими файлами GitHub: версии, хэши, историю, отличия, конфликты и возможную более новую версию.
5. Определи правильную ветку и каталог. Исходники продукта — в соответствующей рабочей ветке; отчёты и инструкции — в `development/`; дизайн и исходные материалы — в предусмотренных каталогах/ветках; большие бинарные артефакты — через Git LFS или утверждённый GitHub release/artifact route, если обычный Git не подходит.
6. Сохрани оригинал, если он нужен для восстановления или проверки; рядом добавь manifest/описание с SHA-256, происхождением, датой, версией, назначением и статусом импорта.
7. Коммить и push в GitHub; затем заново прочитай удалённый файл/ветку и проверь commit SHA, размер/хэш и ссылку.
8. Если неясно, куда положить файл, есть несовместимые версии, риск потери истории или бинарник нельзя загрузить доступным способом — не угадывай и не выбрасывай файл. Запиши BLOCKED и задай владельцу один конкретный вопрос.
9. Не говори «файл сохранён», пока его точная версия не доступна в GitHub и это не проверено.

## 3. Начало каждой сессии: полный контекст и ветка

До изменений:
- Прочитать все обязательные документы и предыдущие пять задач/следующие пять задач в последнем отчёте.
- Проверить GitHub live: default branch, целевую ветку, открытые PR, последний commit SHA, CI/Actions, актуальные отчёты.
- Использовать полный актуальный repository checkout/clone, если доступен; не подменять его частичным архивом. Сохранить необходимые refs, историю, submodules и LFS.
- Проверить `git status`, `git log`, remote refs и соответствие рабочей копии удалённой ветке.
- Создать отдельную task branch от актуальной согласованной базы. Не работать прямо в `main`, если владелец явно не разрешил конкретное исключение.
- Записать исходный SHA и время начала работы в рабочий журнал/отчёт.
- Сначала исследовать существующую реализацию и решения. Не создавать второй механизм, если нужный уже есть.

## 4. Отчёт обязателен после каждого завершённого этапа

После **каждого завершённого этапа**, а также в конце каждой существенной рабочей сессии (даже если этап заблокирован или не завершён), создай отдельный Markdown-отчёт в `development/reports/`.

Имя файла: `YYYY-MM-DD-HHMM-<short-stage-name>.md` (время локальное для Europe/Tallinn). В самом отчёте укажи:
- дату и точное время с часовым поясом;
- автора/тип сессии или модель, если известно (не выдумывать);
- задачу и границы этапа;
- branch, base SHA, head SHA, commit SHA, PR URL;
- файлы добавлены/изменены/удалены и ссылки на них;
- что реально сделано, что не сделано;
- команды и инструменты, которые реально запускались;
- точные результаты тестов: PASS / FAIL / BLOCKED / NOT RUN; ссылки на GitHub Actions run и конкретный SHA;
- ошибки и блокеры, включая сетевые/инструментальные;
- решения владельца и вопросы, требующие его разрешения;
- следующие действия;
- пять предыдущих задач и пять предстоящих задач по правилам раздела 6;
- накопительную оценку готовности по разделу 7.

Не переписывай старые отчёты так, чтобы исчезала история. Создавай новый отчёт, а исправления в старом оформляй отдельной датированной записью или новым документом со ссылкой на исходный. Журнал `development/SESSION-LOG.md` обновляй после каждой сессии, новые записи добавляй сверху.

## 5. Все рабочие файлы должны быть актуальны на GitHub

1. Последняя рабочая версия каждого изменённого/полученного файла должна находиться в правильной ветке GitHub.
2. После каждого логического изменения — commit; после этапа — push и проверка remote HEAD.
3. PR должен содержать цель, scope, base/head SHA, список файлов, проверки, результаты и блокеры.
4. Не оставляй единственный актуальный файл только в чате, локальном workspace, Codespace, Actions artifact или временной ссылке.
5. Актуализируй bundle/архив/manifest на GitHub, когда меняется соответствующий набор исходников. Не создавай лишние копии без версии и назначения. Храни неизменяемые исходные bundles отдельно от новых собранных bundles; не затирай исходный.
6. Для бинарных и крупных файлов используй поддерживаемый механизм GitHub (Git LFS, release asset, Actions artifact с постоянным retention только если это соответствует назначению, или другой одобренный путь). Учитывай, что обычный Actions artifact может истечь: он не заменяет долговременный источник.
7. После загрузки проверь ссылку, размер, checksum и commit/ref. Если проверка невозможна, пометь как BLOCKED.

## 6. Чек-лист пяти предыдущих и пяти следующих задач

В **каждом отчёте** обязательно присутствуют два отдельных списка:
- «Последние 5 предыдущих задач» — пять последних существенных задач/этапов из предыдущих отчётов/журнала, с точным статусом и ссылкой на подтверждение.
- «Следующие 5 задач» — пять ближайших задач по утверждённому плану и зависимостям.

Правило зачёркивания:
- Завершённую задачу отмечай как `~~[x] Название задачи — доказательство/ссылка~~`.
- Незавершённую задачу отмечай `[ ]` и одним из статусов `IN PROGRESS`, `BLOCKED`, `NOT STARTED`.
- Не зачёркивай задачу только потому, что написан код: нужны критерии приёмки и доказательство.
- Если задача завершена в отдельной ветке/PR, но PR не слит, пиши «выполнено в ветке/PR, не слито»; не выдавай её за часть main.
- Сохраняй связь списков между отчётами: переносить пять задач из предыдущего отчёта, закрывать их по доказательствам и добавлять следующие по порядку. Не придумывать историю. Если предыдущих записей нет — честно указать, что ретроспективный список частичный и почему.

## 7. Накопительный процент готовности проекта

Процент — это сквозная оценка проекта, которую продолжает каждый следующий чат. Не начинай оценку с нуля и не подменяй её новой цифрой без объяснения.

Каждый отчёт должен указывать:
1. **Общая готовность InOne, накопительно (%)**.
2. **Готовность текущего релизного этапа (например, Beta 1.0, %)**.
3. При необходимости — готовность ключевых направлений (UI, API, auth, messaging, MLS, files, notifications, infra, QA).
4. Отдельно **готовность реализации** и **готовность подтверждения/верификации**. Наличие кода не равно готовности и не равно прохождению тестов.
5. Baseline предыдущей оценки, дата, автор/источник, методика и объяснение каждого изменения вверх/вниз.

Методика:
- Поддерживай один постоянный weighted work breakdown (WBS) в `development/PROGRESS-BASELINE.md`: направления, вес каждого направления, критерии 0/25/50/75/100%, доказательства и зависимости.
- Общий процент = сумма `вес направления × подтверждённая доля выполнения`; веса всегда суммируются к 100%.
- Не меняй веса и состав работ задним числом, чтобы искусственно повысить результат. Любое изменение WBS — отдельное обоснование и новая версия baseline с сохранением старой.
- Прогресс учитывает только результаты, сохранённые в GitHub и подтверждённые критериями. Непроверенный код учитывается как implementation-in-progress, но не как verified completion.
- Пока единая WBS не создана и не согласована, используй последний опубликованный процент как **предварительный ориентир**, прямо помечай его «оценка, не расчёт по утверждённой WBS», и не заявляй точность. Не усредняй несопоставимые проценты.
- В этом отчёте начальная точка для непрерывности: **InOne в целом — 25%; Beta 1.0 — 35%** (предварительные качественные оценки из аудита 2026-11-09, не измеренная телеметрия и не WBS-расчёт). Следующий исполнитель обязан сначала проверить эти значения по GitHub и сохранить/скорректировать с объяснением, не теряя историю.

## 8. Не подменять документацию сообщением в чате

- Отчёт в чате — только краткое уведомление и ссылки.
- Чат не является отчётным хранилищем, журналом, backlog или continuity.
- Нельзя завершать ответ «готово», если отчёт, журнал и необходимые continuity-документы не обновлены и не проверены на GitHub.
- Если технически нельзя сохранить отчёт, статус сессии — HANDOFF INCOMPLETE; сообщи владельцу, что именно не сохранено. Не представляй ответ в чате как замену.

## 9. Обязательное обновление continuity и bundle

После каждого этапа актуализируй по необходимости:
- `development/SESSION-LOG.md` — всегда после сессии;
- `development/BASELINE-2026-11-08.md` или новый датированный baseline — когда меняется состояние исходников/веток/проверок;
- `development/PROGRESS-BASELINE.md` — при обновлении оценки/WBS;
- `docs/continuity/CURRENT-STATE.md`;
- `docs/continuity/NEXT-SESSION.md`;
- `docs/continuity/SOURCE-OF-TRUTH.md` — при изменении инвентаря артефактов;
- `development/HANDOVER-CHECKLIST.md`;
- bundle/архивный manifest и соответствующую ветку хранения — когда меняется комплект исходников.
Не делай механическое переписывание документов, которые не изменились; в отчёте перечисли, что обновлено и почему, а что проверено без изменения.

## 10. Никаких придуманных решений и постоянных отклонений

1. Не выдумывай требования, API, endpoint, структуру данных, UI, архитектуру, продуктовые решения, разрешения или результаты тестов.
2. Сначала изучи исходники, approved designs, API contracts, decisions и предыдущие PR.
3. Если есть неоднозначность, конфликт версий, риск потери данных, выбор архитектуры, изменение scope, удаление/перемещение файлов или иное решение, которое нельзя однозначно вывести из утверждённых документов, остановись и задай владельцу конкретный вопрос.
4. Разрешение владельца на отклонение действует **только для указанной задачи/операции/сессии**. Не переносить его на другие случаи и не считать постоянным изменением правил, пока владелец отдельно не утвердил это в документации.
5. Записывай каждое полученное решение с датой, областью действия и ссылкой на отчёт/ADR.
6. Не подменяй отсутствующие данные предположениями. Явно помечай INFERRED, UNKNOWN, BLOCKED.

## 11. Merge, release и production safety

1. Не сливать PR, пока все обязательные GitHub Actions checks и требуемые проверки не завершились зелёным статусом на **точном head SHA**, который планируется слить.
2. После любого нового commit проверки запускаются заново/должны относиться к новому SHA. Старый зелёный запуск не подтверждает новый код.
3. Не считать skipped, neutral, pending или отсутствующий check зелёным. Не игнорировать flaky/failing jobs без согласованного решения владельца.
4. Помимо полностью зелёных прогонов, требуется явное разрешение владельца на merge. Это правило не даёт AI права самостоятельно сливать PR.
5. Не выполнять release, deploy, миграцию production DB, изменение production secrets, открытие публичного доступа, изменение DNS или переключение production traffic без отдельного явного разрешения владельца.
6. **Не запускать сервер, dev server, staging, production или любой постоянно работающий сервис без предварительного разрешения владельца.** Не обходить это через Actions, Codespaces, containers или сторонний хостинг.
7. Не публиковать публичный preview или открывать backend/database наружу без разрешения владельца.

## 12. GitHub Actions, Codespaces и доступные возможности

- Всегда проверяй, какие функции GitHub доступны для задачи: Actions/workflows, logs, artifacts, PR checks, branches, releases, Codespaces, environments, security/dependency alerts, issues.
- Используй GitHub Actions для воспроизводимых lint/test/build/validation задач, если workflow уже существует или его добавление однозначно входит в утверждённый scope.
- Используй Codespaces для воспроизводимого полного рабочего окружения, если оно доступно и владелец разрешил создание/использование ресурсов. Не создавай платные ресурсы и не запускай сервисы без разрешения.
- Не объявляй функцию использованной, если она только проверена или недоступна. Указывай конкретный статус: USED / AVAILABLE NOT USED / UNAVAILABLE / NEEDS OWNER APPROVAL.
- Не заменяй Git commit/push ссылкой на Actions artifact или Codespace.

## 13. Качество и проверяемость

- Перед handoff выполнить доступные проверки diff, formatting, lint, unit/integration tests, build и security checks.
- Использовать точные версии toolchain из проекта и CI; не обновлять версии по догадке.
- В отчёте указывать точную команду, среду, SHA, run URL, job, итоги и ограничения.
- Разделять CODE WRITTEN, COMMITTED, PUSHED, CI GREEN, ACCEPTED, MERGED, RELEASED — это разные статусы.
- Сохранять оригинальные дизайны и утверждённые варианты. Не редизайнить без разрешения.
- Не расширять Beta 1.0 scope без решения владельца.

## 14. Обязательный handoff перед завершением

Сессия может считаться завершённой только когда:
- [ ] Все файлы из чата разобраны и помещены в правильные GitHub ветки либо для каждого указан BLOCKED с причиной.
- [ ] Все изменения закоммичены и запушены.
- [ ] Remote branch повторно проверена; SHA подтверждён.
- [ ] Отчёт с датой/временем создан в `development/reports/`.
- [ ] `development/SESSION-LOG.md` обновлён.
- [ ] Пять предыдущих и пять следующих задач отражены с корректным зачёркиванием.
