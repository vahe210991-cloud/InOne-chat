> **Статус документа:** план работ, задачи не считаются выполненными до прохождения критериев приёмки и фиксации результата.
>
> **Область:** локальная регистрация Beta 1.0, вход, управление входом с нового устройства, восстановление доступа и связанные сессии.

## 2. Исходная оценка и правила объёма

По результатам аудита исходного кода выявлены следующие состояния:

- Backend уже содержит базовые маршруты регистрации, входа, refresh/logout, восстановления, отложенного допуска нового устройства и проверки личности после восстановления.
- Базовая регистрация и обычный вход на уже известном устройстве реализованы лучше, чем сквозные мобильные сценарии.
- Главные разрывы находятся на стыке backend и Flutter: подтверждение входа на новом устройстве, дополнительная проверка после recovery, отмена подозрительного допуска и восстановление сессии после перезапуска.
- Наличие тестов в репозитории само по себе не подтверждает, что все сценарии проходят на актуальном SHA. Проверки необходимо выполнить на коммите PR и зафиксировать результат.
- Физические устройства, реальные push-уведомления FCM/APNs и production-доставка не являются обязательными проверками этого плана до релиза Beta 1.0. Обязательны автоматические unit-, integration-, API-, security- и CI-проверки. Для внешних каналов использовать контролируемые тестовые адаптеры и фикстуры.

**Не менять без отдельного согласования:** продуктовую политику обязательности телефона, архитектуру Identity, протоколы MLS и другие контуры, не относящиеся непосредственно к задачам ниже.

## 3. Реестр задач

### Этап A. Сквозной вход и подтверждение нового устройства

#### AUTH-04. Завершить подтверждение входа на новом устройстве — P0

- [ ] **AUTH-04. Поддержать полный сценарий `approval_required` в Flutter.**
  - Backend: проверить существующие маршруты создания approval request, получения/опроса статуса, подтверждения и отклонения входа.
  - Mobile: реализовать экран ожидания подтверждения, отображение понятного статуса, безопасный polling с ограничением частоты и обработку истечения срока действия.
  - На доверенном устройстве обеспечить возможность увидеть запрос и подтвердить либо отклонить его.
  - Секреты подтверждения не должны попадать в логи, аналитику, URL общего назначения или crash reports.
  - При отказе, тайм-ауте, повторном запросе и отзыве сессии UI должен показывать корректное конечное состояние.
  - **Критерии приёмки:** новый девайс не получает полноценную сессию до подтверждения; подтверждённый запрос завершается входом; отклонённый/истёкший запрос не выдаёт токены; повторное использование approval данных не работает.
  - **Тесты:** backend API tests; Flutter unit/widget tests; интеграционный сценарий двух устройств с тестовыми клиентами; negative tests на replay, expiry, polling и отказ.
  - **Зависимости:** согласовать контракт API и фактическую модель статусов до реализации.

#### AUTH-05. Завершить дополнительную проверку личности после recovery — P0

- [ ] **AUTH-05. Поддержать `identity_check_required` в мобильном входе.**
  - Проверить backend-контракт выдачи и проверки `identityCode`, включая срок действия, лимит попыток, повторную отправку и привязку к конкретной попытке входа/устройству.
  - Расширить мобильный API и `InOneSession.login()` так, чтобы дополнительный код можно было безопасно передать и обработать.
  - Добавить экран/состояние дополнительного подтверждения личности и корректный возврат к нему после перезапуска приложения, если это предусмотрено серверным контрактом.
  - Не обходить проверку автоматическим повтором обычного логина и не выдавать полноценную сессию до успешной проверки.
  - **Критерии приёмки:** после завершения recovery новый девайс может пройти дополнительную проверку и войти; неверный/просроченный код не выдаёт сессию; лимиты попыток соблюдаются; успешная проверка не может быть повторно использована для другой попытки или устройства.
  - **Тесты:** backend identity-check tests; Flutter API/unit/widget tests; end-to-end сценарий recovery → login → identity check → session; отрицательные сценарии.
  - **Зависимости:** AUTH-08 (зафиксированная политика каналов подтверждения) и согласованный backend API.

### Этап B. Безопасное управление отложенным входом

#### AUTH-06. Исправить действие «Это не я» — P0/P1

- [ ] **AUTH-06. Развести отмену recovery и отмену отложенного допуска устройства.**
  - Сейчас мобильный экран ожидания входа направляет действие «Это не я» на `POST /recovery/cancel-by-code`, тогда как для отмены отложенного допуска предусмотрен отдельный `POST /admission/cancel`.
  - Проверить точные контракты, авторизацию, одноразовые коды и область воздействия обоих endpoints.
  - Подключить экран «Это не я» к endpoint отмены admission, не затрагивая recovery другого процесса.
  - Проверить, что отмена отзывает/блокирует именно подозрительную попытку входа и не ломает существующие доверенные сессии сверх предусмотренной политикой.
  - **Критерии приёмки:** кнопка отменяет отложенный вход; не вызывает отмену восстановления аккаунта; повторный вызов безопасен; пользователь получает нейтральное подтверждение результата без раскрытия лишней информации.
  - **Тесты:** backend API tests для admission cancel; Flutter widget/API tests; regression test, доказывающий, что recovery state не меняется; idempotency и replay tests.

### Этап C. Надёжное завершение восстановления

#### AUTH-07. Сделать отзыв старых устройств повторяемым и атомарно управляемым — P1

- [ ] **AUTH-07. Исправить финализацию recovery и отзыв прежних устройств.**
  - Текущий риск: recovery window может быть закрыто до того, как последовательно отозваны все старые устройства. При промежуточной ошибке часть устройств может остаться активной, а повторный запуск финализатора не продолжит работу.
  - Ввести устойчивое состояние вроде `revocation_pending`/эквивалентную очередь финализации.
  - Финализатор должен быть идемпотентным, повторяемым после сбоя и иметь однозначное конечное состояние.
  - Предпочесть транзакционное массовое изменение, если модель данных это позволяет; иначе использовать durable progress/outbox и retry с контролем завершения.
  - Не объявлять recovery полностью завершённым, пока все требуемые старые устройства не отозваны.
  - **Критерии приёмки:** сбой после отзыва любого подмножества устройств не оставляет процесс в ложном terminal state; повторный запуск доводит операцию до конца; повторная обработка не наносит побочных эффектов; новые и старые устройства получают предусмотренные права доступа.
  - **Тесты:** fault injection после каждого шага; транзакционные tests; retry/idempotency tests; проверка конкурентного запуска финализатора.

#### AUTH-08. Зафиксировать политику восстановления без подтверждённого телефона — P1, решение продукта

- [ ] **AUTH-08. Утвердить и документировать recovery policy для аккаунтов без verified phone.**
  - В текущем backend для аккаунта с подтверждённой почтой, но без подтверждённого телефона, предусмотрен email-only путь; для legacy-аккаунта без пригодного подтверждённого контакта самостоятельное recovery может быть недоступно.
  - Отдельно описать сценарии: verified phone + verified email; verified email без verified phone; нет доступного verified contact; устаревший/недоступный контакт.
  - Принять продуктово-безопасностное решение: допустим ли email-only recovery для Beta 1.0, какие ограничения/периоды защиты применяются и как обрабатываются legacy accounts.
  - Не считать наличие введённого номера доказательством владения номером. Не менять `INONE_REQUIRE_PHONE` и правила регистрации без отдельного утверждения.
  - Обновить пользовательские тексты, API contract, threat model и документацию по результату решения.
  - **Критерии приёмки:** для каждого класса аккаунта существует однозначный документированный сценарий; backend и Flutter реализуют один и тот же сценарий; нет ложного обещания SMS-подтверждения там, где номер не verified.
  - **Тесты:** тест-матрица по всем классам аккаунтов; tests на отсутствие канала, недоступный канал, истечение кодов и лимиты.
  - **Блокирующее условие:** реализация не должна самостоятельно выбирать более слабую политику восстановления вместо продуктового решения.

### Этап D. Сохранение сессии и восстановление приложения

#### AUTH-09. Обеспечить безопасное восстановление сессии после перезапуска — P1

- [ ] **AUTH-09. Устранить зависимость сохранения сессии от выключенного по умолчанию Native MLS режима.**
  - Проверить фактическую конфигурацию `INONE_MLS_NATIVE_ENABLED` и весь путь сохранения/восстановления refresh token.
  - Сейчас при выключенном Native MLS refresh token может оставаться только в памяти Dart, поэтому после полного перезапуска процесса сессия не восстанавливается.
  - Определить безопасный для Beta 1.0 механизм постоянного хранения токена с использованием системного защищённого хранилища; не сохранять токены в обычных preferences, логах или незашифрованных файлах.
  - Согласовать ownership сессии между Dart и Rust так, чтобы не появилось два независимых источника истины.
  - Учитывать rotation, single-use refresh token, logout, device revocation, reinstall и восстановление из backup.
  - **Критерии приёмки:** после штатного завершения и перезапуска приложения пользователь остаётся авторизованным, если refresh token действителен; logout/revocation немедленно исключает восстановление; replay старого refresh token обрабатывается согласно серверной политике; секреты не попадают в логи.
  - **Тесты:** storage abstraction tests; Flutter integration tests с mock secure storage; restart simulation; refresh rotation/replay/revocation tests; проверка миграции/отсутствия токена.
  - **Ограничение:** не требовать физического устройства до релиза; использовать тестовые реализации платформенного secure storage и автоматизированные интеграционные проверки.

### Этап E. Усиление регистрации и защиты от злоупотреблений

#### AUTH-01. Исключить перечисление зарегистрированных email — P1

- [ ] **AUTH-01. Унифицировать внешние ответы регистрации и подтверждения email.**
  - Сейчас `POST /register/email` использует нейтральный ответ, но `POST /register/email/confirm` может вернуть `409 email already registered` до проверки кода.
  - Изменить поведение так, чтобы неавторизованный клиент не мог определить существование аккаунта по статусу/телу ответа.
  - Сохранить корректную внутреннюю обработку повторной регистрации, лимитов и отправки сообщений.
  - Проверить различия по времени ответа и побочные каналы утечки.
  - **Критерии приёмки:** ответы для существующего и отсутствующего email не раскрывают факт регистрации; корректный владелец получает безопасный следующий шаг; abuse controls продолжают работать.
  - **Тесты:** API regression tests для существующего/несуществующего адреса; проверки кодов ответа и тела; по возможности статистический timing test без нестабильных жёстких порогов.

#### AUTH-02. Сделать погашение registration ticket согласованным с созданием аккаунта — P1

- [ ] **AUTH-02. Устранить окно потери registration ticket при сбое создания аккаунта.**
  - Сейчас ticket погашается отдельной операцией до транзакции создания аккаунта. Сбой БД или конфликт уникальности после погашения может лишить пользователя возможности завершить регистрацию.
  - Перенести consume ticket и создание аккаунта в одну транзакционную границу, если ticket и аккаунт находятся в одной БД.
  - Если это невозможно, реализовать безопасную идемпотентную state machine/outbox с возможностью повторного завершения без повторного использования ticket злоумышленником.
  - Сохранить одноразовость ticket и защиту от гонок.
  - **Критерии приёмки:** регистрация либо создаёт аккаунт и погашает ticket согласованно, либо оставляет возможность безопасно повторить операцию; невозможно создать два аккаунта одним ticket.
  - **Тесты:** fault injection до/после записи аккаунта; параллельные запросы; duplicate nickname/email; rollback/retry; replay ticket.

#### AUTH-03. Согласовать требование телефона и подтверждение владения номером — P1

- [ ] **AUTH-03. Разделить наличие телефона и verified phone.**
  - Проверить default `INONE_REQUIRE_PHONE` и фактическое поведение production-like конфигурации Beta 1.0.
  - В текущем потоке backend может проверять наличие номера, а не подтверждённое владение; SMS flow не должен считаться завершённым только потому, что номер указан в форме.
  - Проверить, подключён ли мобильный экран/шаг SMS verification к реальному API и к выдаче регистрационного допуска.
  - Документировать разницу между `phone_present` и `phone_verified`.
  - **Критерии приёмки:** продуктовая политика Beta 1.0 однозначна; если номер обязателен как подтверждённый, аккаунт не получает статус verified до успешной проверки кода; если номер необязателен, отсутствие номера не блокирует регистрацию в согласованной конфигурации.
  - **Тесты:** конфигурационные tests для true/false; SMS verification positive/negative/expiry/attempt-limit tests; mobile flow tests.
  - **Важно:** не менять политику без продуктового подтверждения. Решение о необязательном телефоне для будущей Identity не является автоматическим изменением Beta 1.0.

#### AUTH-10. Усилить парольную политику — P2

- [ ] **AUTH-10. Проверить и усилить требования к паролю.**
  - Оценить текущий минимум (в исходном аудите обнаружено 8 символов), максимальную длину, обработку Unicode и устойчивость к чрезмерно большим входным значениям.
  - Определить политику против распространённых/скомпрометированных паролей с учётом приватности и доступности сервиса; не отправлять пароль стороннему сервису в открытом виде.
  - Сохранить безопасное хеширование `scrypt`, уникальную соль и constant-time сравнение.
  - **Критерии приёмки:** парольная политика описана и одинаково применяется на клиенте и сервере; сервер остаётся источником истины; большие значения ограничены безопасно; существующие пароли обрабатываются по утверждённой стратегии.
  - **Тесты:** boundary tests, Unicode tests, oversized input tests, common-password policy tests и regression tests для login.

### Этап F. Сквозная приёмка и документация

## 5. Общие требования безопасности и качества

- Не логировать пароли, access/refresh tokens, verification codes, recovery secrets, approval secrets и содержимое приватных deep links.
- Все одноразовые секреты должны иметь ограниченный TTL, лимит попыток, защиту от replay и безопасную привязку к назначению.
- Ошибки должны быть безопасны для пользователя и не раскрывать наличие аккаунта или внутреннее состояние защиты.
- Операции отзыва и завершения recovery должны быть идемпотентными и устойчивыми к повтору после сбоя.
- Не ослаблять существующие rate limits, throttling, PIN или device security без отдельного threat-model обоснования.
- Изменения API должны сопровождаться тестами backend и мобильного клиента.
- Для каждого PR проверять точный SHA, а не переносить статус CI с предыдущего коммита.
- Если CI недоступен, это явно фиксируется как блокирующее ограничение; локальные проверки не объявляются эквивалентом CI.
- Не проводить проверки на физических устройствах до релиза Beta 1.0 в рамках данного плана.

### Инженерные параметры identity challenge

- Срок действия кода: 1 час.
- Повторная отправка: не чаще одного раза в 60 секунд.
- Максимум неверных кодов: 5.
- Блокировка после лимита: 1 час.
- Хэш кода привязан к user ID, device ID и challenge ID.
- При повторном запросе в cooldown активный challenge переиспользуется без повторной отправки письма.
- После истечения lockout лимит попыток сбрасывается; старый challenge недействителен.
