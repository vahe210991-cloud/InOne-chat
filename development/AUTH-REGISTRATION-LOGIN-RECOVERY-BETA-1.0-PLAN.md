## 2. Исходная оценка и правила объёма

По результатам аудита исходного кода выявлены следующие состояния:

- Backend уже содержит базовые маршруты регистрации, входа, refresh/logout, восстановления, отложенного допуска нового устройства и проверки личности после восстановления.
- Базовая регистрация и обычный вход на уже известном устройстве реализованы лучше, чем сквозные мобильные сценарии.
- Главные разрывы находятся на стыке backend и Flutter: подтверждение входа на новом устройстве, дополнительная проверка после recovery, отмена подозрительного допуска и восстановление сессии после перезапуска.
- Наличие тестов в репозитории само по себе не подтверждает, что все сценарии проходят на актуальном SHA. Проверки необходимо выполнить на коммите PR и зафиксировать результат.
- Физические устройства, реальные push-уведомления FCM/APNs и production-доставка не являются обязательными проверками этого плана до релиза Beta 1.0. Обязательны автоматические unit-, integration-, API-, security- и CI-проверки. Для внешних каналов использовать контролируемые тестовые адаптеры и фикстуры.

**Утверждённое продуктовое решение от 2026-11-27:** телефон обязателен как поле регистрации, но SMS-подтверждение владения номером не требуется; номер можно показывать или скрывать в профиле; телефон не используется для восстановления. Восстановление выполняется по одноразовому коду на подтверждённую почту и дополнительному персональному PIN-коду, заданному пользователем при регистрации. Это решение относится к Beta 1.0 и не переносит запуск InOne Identity в первый этап. Архитектуру Identity, протоколы MLS и другие не связанные контуры без отдельного согласования не менять.

## 3. Реестр задач

### Этап A. Сквозной вход и подтверждение нового устройства

#### AUTH-04. Завершить подтверждение входа на новом устройстве — P0

> **Текущий статус PR #171:** экран ожидания и host polling/claim связаны с backend; добавлены Flutter API/widget проверки. Отказ, истечение и точная работа двух устройств остаются на CI/интеграционной приёмке. Задача не закрыта.

- [ ] **AUTH-04. Поддержать полный сценарий `approval_required` в Flutter.**
  - Backend: проверить существующие маршруты создания approval request, получения/опроса статуса, подтверждения и отклонения входа.
  - Mobile: реализовать экран ожидания подтверждения, отображение понятного статуса, безопасный polling с ограничением частоты и обработку истечения срока действия.
  - На доверенном устройстве обеспечить возможность увидеть запрос и подтвердить либо отклонить его.
  - Секреты подтверждения не должны попадать в логи, аналитику, URL общего назначения или crash reports.
  - При отказе, тайм-ауте, повторном запросе и отзыве сессии UI должен показывать корректное конечное состояние.
  - **Критерии приёмки:** новый девайс не получает полноценную сессию до подтверждения; подтверждённый запрос завершается входом; отклонённый/истёкший запрос не выдаёт токены; повторное использование approval данных не работает.
  - **Тесты:** backend API tests; Flutter unit/widget tests; интеграционный сценарий двух устройств с тестовыми клиентами; negative tests на replay, expiry, polling и отказ.
  - **Зависимости:** согласовать контракт API и фактическую модель статусов до реализации.

Backend, PostgreSQL и Flutter tests добавлены; обязательный CI ещё не завершён. Задача не закрыта.

- [ ] **AUTH-05. Поддержать `identity_check_required` в мобильном входе.**

  - Расширить мобильный API и `InOneSession.login()` так, чтобы дополнительный код можно было безопасно передать и обработать.
  - Добавить экран/состояние дополнительного подтверждения личности и корректный возврат к нему после перезапуска приложения, если это предусмотрено серверным контрактом.

  - **Критерии приёмки:** после завершения recovery новый девайс может пройти дополнительную проверку и войти; неверный/просроченный код не выдаёт сессию; лимиты попыток соблюдаются; успешная проверка не может быть повторно использована для другой попытки или устройства.

### Этап C. Надёжное завершение восстановления

#### AUTH-07. Сделать отзыв старых устройств повторяемым и атомарно управляемым — P1

> **Текущий статус PR #171:** сохранён retry финализатора до закрытия recovery window; fault-injection сценарий дополнен повтором через свежий аутентифицированный вход после отзыва старого устройства. Проверка актуального SHA и конкурентные DB tests ещё ожидаются. Задача не закрыта.

- [ ] **AUTH-07. Исправить финализацию recovery и отзыв прежних устройств.**
  - Текущий риск: recovery window может быть закрыто до того, как последовательно отозваны все старые устройства. При промежуточной ошибке часть устройств может остаться активной, а повторный запуск финализатора не продолжит работу.
  - Ввести устойчивое состояние вроде `revocation_pending`/эквивалентную очередь финализации.
  - Финализатор должен быть идемпотентным, повторяемым после сбоя и иметь однозначное конечное состояние.
  - Предпочесть транзакционное массовое изменение, если модель данных это позволяет; иначе использовать durable progress/outbox и retry с контролем завершения.
  - Не объявлять recovery полностью завершённым, пока все требуемые старые устройства не отозваны.
  - **Критерии приёмки:** сбой после отзыва любого подмножества устройств не оставляет процесс в ложном terminal state; повторный запуск доводит операцию до конца; повторная обработка не наносит побочных эффектов; новые и старые устройства получают предусмотренные права доступа.
  - **Тесты:** fault injection после каждого шага; транзакционные tests; retry/idempotency tests; проверка конкурентного запуска финализатора.

#### AUTH-08. Реализовать утверждённую политику восстановления через email и персональный PIN — P1

> **Продуктовое решение утверждено 2026-11-27:** телефон обязателен только как введённое поле регистрации; подтверждать его по SMS не требуется. Телефон не участвует в recovery. При регистрации пользователь дважды вводит персональный PIN восстановления ровно из 8 цифр. Для восстановления обязательны одноразовый код на подтверждённую почту и этот PIN. В профиле раз в 7 дней показывается напоминание с действиями «Помню» и «Не помню, заменить». Не реже одного раза в 30 дней после обычного входа по паролю требуется дополнительная проверка PIN; PIN не заменяет пароль и не является самостоятельным способом входа.

- [ ] **AUTH-08. Реализовать двухкомпонентное восстановление: email-код + персональный PIN.**
  - При регистрации пользователь задаёт PIN восстановления ровно из 8 цифр и дважды вводит его для подтверждения совпадения. Оба поля должны быть цифровыми, с маской/клавиатурой numeric, разрешать ведущие нули и не преобразовывать PIN в число (хранить/передавать как строку). PIN не является паролем входа и не используется для обычной аутентификации.
  - Для recovery сначала отправляется одноразовый код на подтверждённую почту. До успешного прохождения email-проверки PIN не должен давать возможность проверить существование аккаунта или выполнять чувствительные операции.
  - После email-кода пользователь вводит PIN; успешное восстановление требует прохождения обоих факторов в одной ограниченной по времени recovery-сессии. Ни телефон, ни его видимость в профиле не влияют на этот процесс.
  - PIN хранить только как стойкий salted password hash (предпочтительно Argon2id; допустимый текущий KDF выбирать после проверки доступности и параметров в стеке), с индивидуальной солью и защитой от offline/online перебора. Не хранить и не отправлять PIN в открытом виде, не включать его в логи, аналитику, deep links или письма.
  - Ввести независимый лимит попыток PIN, progressive delay/временную блокировку, rate limit по аккаунту и дополнительную защиту от распределённого перебора. Восьмизначный PIN имеет ограниченную энтропию, поэтому запретить неограниченные повторы и обеспечить серверную проверку лимитов; после превышения лимита использовать безопасную задержку и подтверждение через почту, не раскрывая состояние аккаунта. Ответы не должны раскрывать существование аккаунта или корректность отдельного фактора до безопасного этапа.
  - Реализовать недельное напоминание в настройках профиля: не чаще одного раза за 7 дней показывать ненавязчивую строку с вопросом о памяти PIN и действиями «Помню» / «Не помню, заменить». «Помню» фиксирует подтверждение и закрывает напоминание до следующего недельного интервала, но не отменяет ежемесячную проверку. «Не помню, заменить» запускает защищённую смену PIN: подтверждённая почта + текущая парольная сессия/повторная аутентификация; новый PIN вводится дважды, отправляется уведомление о смене, старый PIN немедленно становится недействительным. Если пользователь не может войти, применяется отдельный recovery-процесс, нельзя обходить его одним email-кодом.
  - Реализовать ежемесячную проверку памяти PIN: не реже одного раза в 30 дней после успешного обычного входа по паролю приложение требует ввести правильный 8-значный PIN до открытия защищённой части аккаунта. Учитывать серверное время и хранить дату последней успешной проверки; не сбрасывать интервал простым перезапуском приложения или сменой локальных часов. Не превращать PIN в самостоятельный фактор входа: пароль остаётся обязательным, а email recovery остаётся отдельным процессом. Ошибки PIN ограничиваются и журналируются без записи самого PIN.
  - Уточнить UX и API contracts: телефон обязателен при регистрации, не требует SMS verification; настройка видимости телефона доступна владельцу профиля; recovery требует verified email + PIN.
  - **Критерии приёмки:** регистрация не завершается без номера и двух совпадающих 8-значных PIN-полей; допускаются ведущие нули; номер сохраняется без ложного статуса verified; PIN не раскрывается и не восстанавливается из БД; recovery не завершается только по email-коду; оба фактора привязаны к одному challenge и ограниченному TTL; PIN brute-force/replay/race сценарии безопасно отклоняются; недельное напоминание показывается по расписанию и оба ответа работают; ежемесячная PIN-проверка обязательна после входа и не обходится перезапуском/сменой времени; смена PIN требует подтверждённой почты и повторной аутентификации, отправляет уведомление и аннулирует старый PIN.
  - **Тесты:** регистрация с отсутствующим/валидным номером; формат PIN ровно 8 цифр, ведущие нули, mismatch двух полей; хранение и проверка хеша; неверный PIN, истечение, повтор, параллельные запросы, лимит попыток, блокировка, распределённый перебор, email-код без PIN, PIN без email-кода; недельное расписание, ответы «Помню»/«Не помню, заменить», повторное появление; месячный gate по серверному времени, clock tampering, app restart; смена PIN, уведомления и privacy/non-enumeration.
  - **Текст ежемесячного запроса:** «Просим прощения за временные неудобства. Мы заботимся о безопасности вашего аккаунта и хотим защитить его от постороннего доступа. Пожалуйста, подтвердите PIN-код восстановления.»
  - **Технические ограничения:** PIN всегда строка из 8 ASCII-цифр `0–9`, включая ведущие нули. Хешировать Argon2id с индивидуальной солью и параметрами, откалиброванными под сервер; не использовать быстрый SHA-хеш. Из-за пространства всего в 100 млн комбинаций применять строгие серверные лимиты, progressive delay и блокировку. Не логировать PIN ни на одном слое.

## 5. Общие требования безопасности и качества

- Не логировать пароли, access/refresh tokens, verification codes, recovery secrets, approval secrets и содержимое приватных deep links.
- Все одноразовые секреты должны иметь ограниченный TTL, лимит попыток, защиту от replay и безопасную привязку к назначению.
- Ошибки должны быть безопасны для пользователя и не раскрывать наличие аккаунта или внутреннее состояние защиты.
- Операции отзыва и завершения recovery должны быть идемпотентными и устойчивыми к повтору после сбоя.
- Не ослаблять существующие rate limits, throttling, PIN или device security без отдельного threat-model обоснования.
- Изменения API должны сопровождаться тестами backend и мобильного клиента.
- Для каждого PR проверять точный SHA, а не переносить статус CI с предыдущего коммита.
- Если CI недоступен, это явно фиксируется как блокирующее ограничение; локальные проверки не объявляются эквивалентом CI.
- Не проводить проверки на физических устройствах до релиза Beta 1.0 в рамках данного плана.
