# Stable OpenMLS 0.9.2 SQLCipher compatibility prototype

This prototype is intentionally isolated from the production MLS client.

## Compatibility contract

- Legacy writer: OpenMLS 0.8.1 with `openmls_sqlite_storage 0.2.0`.
- Candidate reader: stable OpenMLS 0.9.2 with `0-8-1-storage-format`.
- Legacy database: SQLCipher encrypted, with a persisted MLS group and private signing key.
- Candidate SQLCipher: SQLCipher 4.20.0 / SQLite 3.54.1 via `rusqlite 0.42.0` and `libsqlite3-sys 0.40.0`.
- Candidate storage and credential source snapshots are documented in `vendor/README.md`.

The workflow is a prototype gate only. It does not change production dependencies or assert that all historic device databases are migrated. Production adoption requires the full mobile platform matrix and MLS interoperability tests.

## Reproducibility and runtime assertions

The candidate reader checks the runtime values reported by SQLite and SQLCipher after applying the database key: SQLite must report `3.54.1` and SQLCipher must report `4.20.0`. A crate-version floor alone is not treated as proof of the linked runtime.

The runner generates separate lockfiles for `legacy-writer` and `current-reader`, validates the intended package/version contracts (including patched `crypto-bigint 0.7.11`, `libcrux-kem 0.0.10`, `libsqlite3-sys 0.40.0`, `refinery-core 0.10.1`, and exact `rusqlite 0.42.0`), prints SHA-256 digests for both lockfiles, and uses `--locked` for fixture generation and candidate tests. The workflow file is intentionally unchanged on this branch: its current artifact step retains only the candidate lockfile and candidate RustSec JSON report. It does not retain the generated fixture, legacy lockfile, legacy RustSec report, or the SHA-256 output as artifacts. The legacy-writer graph is checked for its expected OpenMLS 0.8.1 package versions by the runner, but a separate RustSec audit for that graph is not currently part of the workflow.

Lockfiles are generated by the runner and are not yet committed as reviewed, immutable inputs. Production adoption requires reviewing and committing both generated lockfiles, then rerunning the full compatibility and platform matrix against those exact files.

## Candidate coverage added on the isolated hardening branch

The source-level test matrix now includes:

- Libcrux-created Welcome accepted by RustCrypto, and RustCrypto-created Welcome accepted by Libcrux.
- Application messages in both provider directions.
- Provider-backed Ed25519 key generation for both providers.
- `MaxPastEpochs(16)`: a retained prior-epoch message can be decrypted once, replay is rejected, and an epoch-1 message is rejected after the retention window has elapsed.
- An MLS membership-removal transition rolled back through a caller-owned SQLCipher transaction.
- A multi-member, multi-epoch OpenMLS 0.8.1 SQLCipher fixture, with a retained Alice/Bob group at epoch 3.
- Decryption of an authentic epoch-1 message from that 0.8.1 fixture after the 0.9.2 reader loads epoch 3, using both Libcrux and RustCrypto.
- Idempotent application of all six storage migrations and presence of the expected virtual-client tables.

These are test cases added to source, not passing results. No compilation, formatting check, RustSec run, or test execution has been performed on this branch. Migration process-kill recovery remains outstanding.
