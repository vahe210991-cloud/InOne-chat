# InOne Bots & Stickers — архитектурная основа и функциональные требования

**Статус:** проектное предложение по запросу владельца от 2026-11-16; документ фиксирует целевую архитектуру и требования, но не означает реализацию или включение функций в Beta 1.0.  
**Область:** платформа ботов, интеграция внешних программ/конструкторов, официальный Bot Manager и официальный Sticker Bot.

## 1. Цель

Создать в InOne расширяемую платформу ботов. Бот — отдельная системная сущность с собственным Bot ID, публичным профилем, владельцем, настройками, разрешениями и отзываемыми API credentials.

Платформа должна позволять:
- создавать и регистрировать ботов внутри InOne через официального главного бота;
- подключать собственный сервер разработчика, AI-агента, CRM, сценарий автоматизации или сторонний визуальный конструктор;
- принимать события InOne через Webhooks и вызывать функции InOne через REST API;
- добавлять ботов в личные диалоги и группы только с явного разрешения пользователей/администраторов;
- запускать системных ботов, принадлежащих администрации InOne, включая Sticker Bot.

Это отдельный платформенный модуль. Он не должен становиться зависимостью регистрации, авторизации, обычных чатов или работы MLS.

## 2. Роли и владение

### 2.1. Главный бот — InOne Bot Manager

Официальный системный бот, принадлежащий администрации InOne. Он является пользовательским интерфейсом для регистрации и управления ботами, но не единственным компонентом безопасности: все проверки выполняются серверным Bot Platform API.

Команды/разделы:
- Создать бота
- Мои боты
- Настройки и описание
- API-токен и подключение
- Разрешения
- Webhooks / проверка подключения
- Остановить / запустить
- Отозвать токен / выпустить новый
- Передать владение (только если политика платформы это разрешает)
- Удалить бота / запросить удаление

Bot Manager и другие системные боты имеют владельца типа `platform`, не обычного пользователя. Изменение их настроек доступно только уполномоченным администраторам и фиксируется в аудите.

### 2.2. Внешний разработчик

Пользователь InOne, которому разрешено создавать ботов. На первом этапе владелец бота — аккаунт пользователя, создавшего его. В дальнейшем можно добавить командное владение/организации с ролями Owner, Admin и Developer.

### 2.3. Системный бот

Бот, созданный и контролируемый администрацией InOne. Его нельзя присвоить пользователю, передать или удалить обычными командами Bot Manager. Для системных ботов действуют те же технические ограничения, аудит и изоляция, что и для внешних ботов; административный статус не должен давать скрытый доступ к пользовательским сообщениям.

## 3. Предлагаемый процесс регистрации

1. Пользователь открывает в InOne верифицированный чат с **InOne Bot Manager** и нажимает «Создать бота».
2. Bot Manager показывает правила платформы, ограничения и предупреждение о том, что токен является секретом.
3. Пользователь вводит отображаемое имя, уникальный username, краткое описание, категорию и контакт разработчика/сайт (последнее необязательно).
4. Backend проверяет права пользователя, формат и уникальность username, лимиты создания, запрещённые имена и признаки злоупотребления.
5. Создаётся запись бота со статусом `PENDING_SETUP`, уникальным неизменяемым Bot ID и владельцем.
6. Система генерирует один секретный API-токен. Bot Manager показывает его только один раз и предлагает скопировать. В базе хранится только криптографический хеш/верификатор токена, а не исходное значение.
7. Разработчик вставляет токен в секреты своего сервера или в поле credentials поддерживаемого конструктора. Токен нельзя помещать в исходный код, мобильное приложение, публичный репозиторий, URL или клиентский JavaScript.
8. Разработчик настраивает Webhook URL (если нужен), подтверждает владение endpoint через challenge и выбирает минимальный набор scopes.
9. Backend проверяет формат endpoint, TLS/HTTPS, challenge, права и лимиты. На первом этапе бот может работать в режиме личного тестирования.
10. При запросе доступа к группам, массовым рассылкам, файлам или другим чувствительным функциям требуется отдельное одобрение платформы. До одобрения такие scopes недоступны.
11. После успешной проверки бот получает статус `ACTIVE`. Пользователь может в любой момент остановить бота или отозвать credentials.

### Статусы

`PENDING_SETUP` → `ACTIVE` → `SUSPENDED` / `REVOKED` / `DELETION_PENDING` → `DELETED`.

Переходы выполняются только сервером по проверяемым правилам. Suspended/Revoked бот не может отправлять сообщения, получать события или использовать API.

### Почему регистрация через главного бота

Это понятный пользователю единый интерфейс, похожий по концепции на BotFather, но регистрация, токены, проверка Webhooks, лимиты и права остаются на сервере. Поэтому смена интерфейса Bot Manager не требует изменения API, а сторонний конструктор не получает административные полномочия.

## 4. API для сторонних программ и конструкторов

### 4.1. Базовая схема

- **REST API** — исходящие действия бота: отправка сообщения, ответ на команду, получение профиля/контекста в пределах разрешённых scopes, отправка стикера/вложения, управление webhook-подписками.
- **Webhooks** — доставка событий InOne на endpoint разработчика: входящее сообщение, команда, добавление/удаление бота из чата, callback от интерактивной кнопки, событие доставки и доступные события стикеров.
- **Версионирование** — префикс версии, например `/api/bot/v1/...`; несовместимые изменения — только в новой версии.
- **OpenAPI** — публикуемый контракт с примерами, схемами ошибок, лимитами, scopes и правилами повторной доставки.
- **SDK** — официальные библиотеки для популярных серверных языков могут появиться позже; API не должен зависеть от конкретного языка/поставщика конструктора.

Сторонний конструктор подключается как обычный API-клиент: разработчик вставляет выданный InOne токен, задаёт разрешённые события и URL обработчика. InOne не должен требовать отдельную интеграцию с каждым конструктором, если тот умеет делать HTTPS-запросы и принимать Webhooks.

### 4.2. Токены и безопасность

- Секрет создаётся криптографически стойким генератором; полный токен показывается один раз.
- Хранить только хеш/верификатор с подходящей схемой для высокоэнтропийных секретов; не писать токены в логи, аналитику, трассировки или сообщения об ошибках.
- Токен имеет идентификатор/префикс для отображения в панели, дату создания, последнего использования, scopes, статус и срок действия/политику ротации.
- Разрешить немедленный отзыв и выпуск нового токена. Ротация может предусматривать короткий контролируемый overlap двух токенов.
- Поддержать несколько отдельных credentials для окружений (например, test и production) на более позднем этапе; не переиспользовать один токен между разными ботами.
- Все запросы идут только по HTTPS. Авторизация передаётся в заголовке, не в query string.
- Webhook подписывается HMAC с секретом подписи; проверяются timestamp и подпись, чтобы предотвращать подделку и replay.
- Доставка Webhook имеет event ID, ограниченные повторы с backoff, дедупликацию и понятный статус доставки.
- Ограничить частоту запросов, размер тела, число параллельных задач и объём хранения; лимиты должны быть видны разработчику.
- Webhook endpoint защищается от SSRF: запрет loopback/private/link-local адресов, повторная DNS-проверка и безопасная политика redirect; разрешать только HTTPS.
- Любые изменения scopes, владения, токенов и статуса записываются в неизменяемый audit log.

### 4.3. Модель scopes

Новый бот получает минимальные права. Предлагаемые отдельные scopes:
- `profile.read.basic` — базовая публичная карточка бота/собеседника в разрешённом контексте;
- `messages.receive` — получать события сообщений только в чатах, где бот явно добавлен;
- `messages.send` — отправлять сообщения от имени бота в разрешённых чатах;
- `commands.receive` — получать команды, адресованные боту;
- `files.receive` / `files.send` — работать с файлами в рамках лимитов и политики хранения;
- `stickers.use` — отправлять стикеры из доступных наборов;
- `groups.join` — принимать приглашение в группу после одобрения администратора;
- `members.read.basic` — получать только минимальные данные участников, необходимые для конкретного сценария.

Не вводить широкие scopes вида «читать все чаты», «полный доступ к аккаунту» или «администратор». Каждый scope проверяется сервером на каждом запросе, а не только при выдаче токена.

### 4.4. Добавление бота в диалог или группу

- Пользователь может начать личный диалог с ботом по его профилю/username.
- Добавление бота в группу выполняется через приглашение и подтверждение администратора группы.
- Перед подтверждением показываются имя бота, разработчик, запрашиваемые scopes и краткое объяснение.
- Администратор может отключить отдельные разрешения, удалить бота или запретить ему отвечать.
- Бот получает только события после присоединения и только в пределах scopes. История чата до добавления не передаётся по умолчанию.
- Удаление бота немедленно прекращает доставку событий и отправку сообщений в этот чат.

## 5. Совместимость с E2EE / MLS — обязательная граница

Платформа ботов не должна обходить MLS и не должна создавать скрытый серверный доступ к содержимому чатов.

- Бот в E2EE-диалоге/группе является явным участником диалога, а не невидимым серверным слушателем.
- Добавление бота в MLS-комнату требует явного согласия и корректного включения бота как участника/клиента в MLS-группу по отдельному утверждённому протоколу.
- Пользователям до добавления показывается предупреждение: сообщения, доступные боту как участнику, будут передаваться на инфраструктуру разработчика бота.
- До готовности MLS-участия ботам запрещено получать plaintext содержимое MLS-чатов. Никакого plaintext fallback и серверного обхода.
- Внешний webhook получает только события, которые разрешено раскрывать конкретному боту и которые действительно доступны ему как участнику.
- Секреты MLS, ключи комнат, ключи устройств и refresh tokens никогда не передаются стороннему боту или конструктору.
- Отправляемые ботом сообщения и стикеры в E2EE-чат должны проходить штатный MLS encrypt/decrypt pipeline.

Это требование является блокирующим архитектурным условием для включения ботов в MLS-чаты.

## 6. Официальный Sticker Bot

**Sticker Bot** — отдельный системный бот InOne, принадлежащий администрации платформы. Он регистрируется как системный бот, не как пользовательский бот, и использует общую Bot Platform инфраструктуру и отдельный сервис обработки изображений.

### 6.1. Сценарий «фото → стикер»

1. Пользователь открывает официальный Sticker Bot и отправляет фотографию.
2. Бот проверяет тип, размер и безопасность входного файла; при необходимости отклоняет неподдерживаемый формат.
3. Сервис обработки выделяет основной объект, удаляет фон (если это возможно), кадрирует изображение и добавляет аккуратную обводку/контур.
4. Пользователь видит предпросмотр и может принять результат или повторить обработку с другим стилем/кадрированием.
5. Сервис создаёт оптимизированный стикер с прозрачностью и сохраняет исходный/производный файл по утверждённой политике хранения.
6. Sticker Bot отправляет готовый стикер в диалог и предлагает «Добавить в подборку» или «Создать стикерпак».

Пользователь может отправить фото, на котором изображены люди, животные, предметы, рисунки или другие объекты. Обработка не должна автоматически публиковать результат: публикация и добавление в общий набор требуют явного действия пользователя.

### 6.2. Формат и обработка

- Поддерживать прозрачный фон там, где формат результата это позволяет.
- Создавать нормализованный файл с ограничениями на размер в пикселях, вес, число кадров и допустимые форматы; точные лимиты определить в API contract перед реализацией.
- Хранить метаданные: владелец, дата создания, source asset reference, версия обработки, mime type, размеры, hash, статус модерации и политика доступа.
- Обрабатывать входные изображения в изолированном worker/service; не исполнять содержимое файла и удалять EXIF/лишние метаданные, если они не нужны.
- Не передавать исходные фотографии сторонним AI/image API без отдельного раскрытия пользователю и утверждения провайдера/условий обработки.
- Предусмотреть жалобы, удаление незаконного/нарушающего права контента и защиту от вредоносных файлов.

### 6.3. Личные подборки и стикерпаки

Термины:
- **Стикер** — отдельное изображение с уникальным Sticker ID.
- **Стикерпак** — именованный набор стикеров с обложкой, автором, видимостью и версией.
- **Подборка пользователя** — список стикерпаков и/или отдельных стикеров, которые пользователь добавил для быстрого использования.

Правила:
- Один стикерпак содержит **не более 50 стикеров**. Это жёсткое серверное ограничение, а не только ограничение интерфейса.
- Проверять лимит при создании, импорте и каждом добавлении; 51-й стикер должен отклоняться с понятной ошибкой.
- У пользователя может быть несколько собственных стикерпаков; отдельный общий лимит наборов/хранилища задаётся политикой квот.
- Владелец может переименовать набор, изменить обложку, порядок стикеров, добавить или удалить стикер, изменить видимость и удалить набор.
- Публичный/доступный по ссылке набор можно открыть по уникальному deep link и просмотреть до добавления.
- Кнопка «Добавить стикерпак» добавляет ссылку на набор в личную подборку пользователя; это не передаёт авторство и право собственности.
- При обновлении набора создаётся новая версия. Добавившие набор пользователи по умолчанию получают актуальную версию; можно предусмотреть отключение автообновления.
- Удаление/снятие с публикации набора прекращает новые добавления и делает ссылку недоступной. Политика уже добавленных копий/кэша должна быть определена отдельно с учётом жалоб, авторских прав и требований удаления.
- Пользователь может удалить набор из своей подборки, не удаляя оригинал автора.
- Для отправки стикера в чат клиент использует Sticker ID/версию и получает бинарный asset через защищённый media flow. В MLS-чатах отправка должна соответствовать правилам раздела 5.

### 6.4. Предлагаемые экраны Sticker Bot

- Старт: «Создать стикер», «Мои стикерпаки», «Популярные наборы», «Помощь».
- Результат обработки: предпросмотр, повторная обработка, сохранить.
- Редактор набора: название, обложка, порядок, список до 50 стикеров.
- Просмотр набора: автор, описание, число стикеров, предпросмотр и кнопка добавления.
- Личная подборка: добавленные наборы, избранные стикеры, удаление из подборки.

## 7. Предлагаемые сущности данных

Минимальная логическая модель (не физическая схема БД):

- `bots`: bot_id, owner_type, owner_id, username, display_name, description, status, created_at, updated_at.
- `bot_credentials`: credential_id, bot_id, token_hash, token_prefix, scopes, status, created_at, expires_at, last_used_at, revoked_at.
- `bot_webhooks`: webhook_id, bot_id, endpoint, signing_secret_reference, subscribed_events, status, verified_at.
- `bot_installations`: installation_id, bot_id, conversation_id, installed_by, approved_scopes, installed_at, revoked_at.
- `bot_events`: event_id, bot_id, event_type, payload_reference, delivery_status, attempts, created_at.
- `stickers`: sticker_id, owner_id, asset_reference, metadata, moderation_status, created_at.
- `sticker_packs`: pack_id, owner_id, title, description, cover_sticker_id, visibility, version, status.
- `sticker_pack_items`: pack_id, sticker_id, position; уникальность пары и ограничение максимум 50 элементов на pack_id.
- `user_sticker_collections`: user_id, pack_id, added_at, auto_update_enabled.
- `bot_audit_events`: actor_id, bot_id, action, metadata_redacted, created_at.

Физическая схема, индексы, миграции, retention и API DTO проектируются отдельно после согласования контракта. Не создавать миграции только на основании этой концептуальной модели.

## 8. Администрирование и модерация

Административная панель должна показывать:
- список ботов, владельцев, статусов, созданных credentials и последних использований;
- scopes и разрешения, webhook health, ошибки доставки, rate-limit counters;
- жалобы, блокировки, историю изменений и административные действия;
- отдельную маркировку системных ботов и защищённые операции для них.

Администраторы могут приостановить бота, отозвать credentials, отключить Webhook и ограничить распространение стикерпака. Все такие действия требуют причины и записи в audit log. Не использовать административные полномочия для скрытого чтения пользовательских чатов.

## 9. Этапы реализации — предложение, не изменение WBS

1. **Foundation / contracts:** утвердить bot lifecycle, API/OpenAPI, scopes, Webhook signing/retry, quotas, audit и threat model.
2. **Bot Manager:** системная регистрация, Bot ID, профиль, credentials, scopes, тестовый режим, отзыв/ротация.
3. **Developer integration:** REST API, Webhooks, документация, тестовый бот и примеры для внешнего конструктора.
4. **Conversation integration:** личные диалоги, групповые приглашения, пользовательское согласие, отключение и модерация.
5. **Sticker service:** обработка фото, предпросмотр, Sticker ID и личная подборка.
6. **Sticker packs:** создание/редактирование наборов, hard limit 50, ссылки, добавление другим пользователям, версии и обновления.
7. **MLS acceptance:** отдельная проверка, что бот — явный MLS участник и все сообщения/стикеры идут только по E2EE pipeline.

Каждый этап имеет собственные API-контракты, миграции, тесты, security review и acceptance criteria. До прохождения соответствующего этапа UI не должен показывать функцию как доступную.

## 10. Критерии приёмки

### Bot Platform
- Нельзя зарегистрировать дублирующий username или создать бота без разрешённого владельца.
- Токен показывается один раз, в базе нет его открытого значения, токен можно отозвать/ротировать.
- API отклоняет запрос без токена, с неверным/отозванным токеном и с недостаточным scope.
- Webhook challenge, подпись, timestamp, повторная доставка и дедупликация проверены тестами.
- Rate limits, SSRF-защита, аудит, suspend/revoke и удаление проверены.
- Бот не получает историю до установки и не получает события за пределами согласованных scopes.
- Бот не может читать MLS plaintext до явного включения в MLS-группу; отсутствует обход E2EE.

### Sticker Bot
- Корректное фото создаёт предпросмотр стикера; некорректный/слишком большой файл отклоняется.
- Пользователь может сохранить отдельный стикер и создать набор.
- Создание 50-го стикера успешно, попытка добавить 51-й отклоняется на backend.
- Другой пользователь может открыть набор и добавить его в личную подборку.
- Удаление из личной подборки не удаляет оригинал.
- Обновления набора версионируются; права автора и политика удаления соблюдаются.
- Отправка стикера в E2EE-чат не обходит MLS.

## 11. Границы и открытые вопросы

- Это архитектурное предложение; оно не утверждает, что Bot API, Bot Manager, Sticker Bot, обработка изображений, Webhooks или sticker-pack storage уже существуют.
- Не добавлять эту работу в Beta 1.0 и не менять WBS v1.1 без отдельного решения владельца. В действующей WBS permissioned bots уже упомянуты как кандидат group-collaboration extras для Beta 2.0; полноценную общую Bot Platform и Sticker Bot следует отдельно оценить и распределить по релизам.
- До разработки требуется отдельное согласование: кто может создавать ботов и какие лимиты действуют; какие scopes доступны без модерации; видимость/публикация стикерпаков; лимиты входных фото и итогового файла; срок хранения оригинальных фото; использование сторонних AI/image провайдеров; правила удаления и авторских жалоб.
- Точные REST paths, event names, payloads, DTOs, HTTP status codes, rate limits, quotas и sticker media format не фиксируются до отдельного API contract review.
- Системные боты принадлежат администрации InOne и не могут быть присвоены пользователями.

## 12. Связанные архитектурные ограничения

- Beta 1.0 использует независимый InOne backend/database; эта функция не должна вводить runtime dependence on Propo.
- Существующие правила MLS, защищённого хранения ключей и fail-closed поведения сохраняются.
- Бинарные файлы стикеров должны использовать отдельный media/storage contract; для E2EE-сообщений применяются уже утверждённые encrypted attachment boundaries, а не новая plaintext-загрузка.
- Реализация должна быть добавлена в актуальный backend/mobile source tree после согласования контрактов; архивный 0.6.0 код не считать автоматически текущей точкой интеграции.
