# Feed Beta 1.0 API contract proposal

**Status:** DRAFT — revised to media-first architecture; owner review required before production routes, schema, or Flutter integration.
**Baseline:** main at 7d34b99fcc026a828b838e211d039c575aeace1d.
**Decision:** owner approved Feed media variant A on 2026-11-27: a separate server-side media-processing pipeline, TLS in transit, encrypted object storage at rest, mandatory authenticated access and re-authorization at delivery. Chat MLS/file pipeline is out of scope and must not be modified.

## 1. Binding product rules

1. Feed and visual publications are part of InOne Beta 1.0.
2. A publication MUST contain at least one successfully processed photo or video. Caption is optional. Text-only publication is rejected by the backend.
3. Every publication shown in the general Feed is readable by every registered account with a currently active authenticated session. Anonymous access is denied.
4. Nickname is required in the author presentation. Internal user/account/device identifiers MUST NOT be returned.
5. Feed media inherits the parent publication's read eligibility, but every media request independently re-authenticates the current session and re-checks publication/media state. IDs and URLs are never authorization credentials.
6. Existing privacy variant В remains binding for profile information and all non-Feed account data. General Feed publication visibility does not make the whole profile public and does not add follow/block/social-graph permissions.
7. The new Feed media pipeline is isolated from the existing chat/MLS file pipeline: no change to MLS encryption, room file handling, current chat object semantics, or existing file authorization.
8. Native Flutter/Dart screens remain the UI target. Do not restore HTML/WebView or replace accepted designs without necessity and owner approval.

## 2. Domain model

### Post

- postId: opaque random identifier generated by the server.
- authorId: internal foreign key, never serialized in public Feed DTO.
- caption: nullable normalized plain text; absent/blank becomes null.
- status: published, deleting, or deleted (draft/upload staging is represented by upload/media lifecycle, not a visible post).
- createdAt, updatedAt: server-owned timestamps.
- revision: monotonic integer for optimistic concurrency.
- idempotencyKeyHash: scoped to author and operation; raw key is not persisted.

### PostMedia

A post has one or more ordered media associations. Each association references a Feed-owned media record, never an arbitrary object key supplied by the client.

- mediaId: opaque random identifier.
- postId: parent association.
- position: server-validated ordering.
- kind: image or video.
- processingStatus: quarantined, processing, ready, rejected, deleting, deleted.
- originalObjectKey, renditionObjectKeys: private server-generated storage keys.
- sha256, byte size, detected media type, dimensions/duration and processing metadata.
- createdAt, readyAt, deletedAt.

A publication may be committed only when every attached media item is ready, the count is at least one, and all media records are owned by the authenticated author and reserved for that publication request. The server never accepts object-storage keys from a client.

## 3. Media lifecycle and trust boundaries

### 3.1 Upload reservation

POST /media/uploads requires an active authenticated device session and accepts declared media intent (kind, byte size, checksum, idempotency key). The server applies configurable policy limits, creates a random media ID and random private quarantine object key, and binds the reservation to author + device + expiry. Declared MIME and extension are hints only.

The upload reservation is single-use. Replays, conflicting retries, expired reservations, wrong-device completion and revoked-device completion fail closed. The server enforces the actual byte limit while streaming, not only from the declared size.

### 3.2 Upload transport

PUT /media/uploads/:mediaId/content uses TLS and a short-lived upload authorization bound to the authenticated reservation. Object storage remains private. The endpoint must enforce content-length/stream byte bounds, request timeout, checksum, and no path/key supplied by the client. Do not return a permanent or anonymous object URL.

### 3.3 Quarantine and validation

After upload, the media remains quarantined and is not attachable/readable. A separate Feed processing worker:

1. verifies SHA-256 against the streamed bytes;
2. detects file type from bytes/container structure, not extension or client MIME;
3. parses/decodes with maintained libraries in a resource-limited isolated process;
4. rejects malformed, truncated, polyglot/unsupported or policy-exceeding media;
5. strips or normalizes risky metadata such as EXIF location where appropriate;
6. produces server-controlled image thumbnails and video poster/preview renditions;
7. stores original and renditions under private random object keys with encryption at rest;
8. records the verified metadata and marks the media ready only after all required objects are durable.

Processing failures leave the item unavailable and schedule safe cleanup. No untrusted media is served inline before validation. Browser/mobile responses set safe content type, X-Content-Type-Options: nosniff, restrictive cache policy and safe content disposition where relevant.

### 3.4 Encryption and key management (owner-approved variant A)

- TLS is mandatory for client ↔ API, worker ↔ storage and internal processing connections.
- Feed objects use a dedicated private bucket/container or isolated storage namespace, separate from chat/MLS objects.
- At-rest protection should use envelope encryption: per-object data encryption key (DEK), authenticated encryption (AES-256-GCM or storage-provider equivalent), and a KMS/HSM-managed key-encryption key (KEK). KEKs and plaintext DEKs must not be stored in application tables or logs.
- The worker receives narrowly scoped decrypt/encrypt permissions only for the Feed quarantine/processing namespace. Runtime credentials are short-lived and least-privilege.
- Database rows store opaque object keys, checksums and key-version metadata, never raw keys.
- Backups, replicas, thumbnails, previews and temporary files must receive equivalent encryption and access controls.
- Rotation and deletion must include originals, renditions, replicas, backups according to documented retention guarantees.
- This is server-side media processing, not E2EE. This decision applies only to Feed media and does not alter chat MLS.

### 3.5 Publish and association

POST /posts accepts an optional caption, an idempotency key and an ordered list of opaque media IDs. It does not accept media bytes, object keys, owner IDs, timestamps, status or public URLs.

Within a transaction the backend verifies:
- active author session;
- one or more unique media IDs;
- every media row is ready, Feed-scoped, owned by the authenticated author, not expired/deleting/already consumed, and reserved for this publication;
- media count/order comply with the server's configured policy;
- idempotency semantics match the original canonical request.

The transaction creates the post and associations and consumes the upload reservations atomically. A post is not visible until its database transaction commits.

### 3.6 Delivery and authorization

GET /media/:mediaId and rendition delivery are authenticated API operations, not public object URLs. For every request the server:
- validates the current active session and device state;
- resolves media → post association from trusted database state;
- confirms post is published and not deleted/deleting;
- applies the approved general-Feed read rule;
- verifies the requested rendition belongs to that media;
- streams the object through the authenticated service or issues a very short-lived, device/session-bound storage capability only if the service can guarantee immediate revocation semantics.

Preferred Beta 1.0 behavior is authenticated API proxy/streaming. Do not issue long-lived bearer URLs. Device revocation must deny subsequent media requests. Cache policy must not allow shared/public caching or stale access after revocation.

### 3.7 Delete and cleanup

Deleting a post is an owner-only transactional state transition. The post becomes immediately unavailable to Feed/detail/media reads. In the same transaction, enqueue an idempotent cleanup/outbox event and mark associated media deleting. A worker deletes originals, renditions and temporary artifacts; retries are safe. Retain only minimal tombstone/audit metadata for the documented period. Do not delete shared objects unless ownership/reference checks prove they are unreferenced. Cleanup failure must be observable and must never restore read access.

## 4. Proposed HTTP API

All routes require a currently active authenticated device session. No anonymous endpoints.

| Method and route | Purpose | Authorization |
|---|---|---|
| POST /media/uploads | Reserve a Feed media upload | Authenticated author |
| PUT /media/uploads/:mediaId/content | Upload bytes into quarantine | Reservation owner + bound active device |
| POST /media/uploads/:mediaId/complete | Verify upload and enqueue processing | Reservation owner + bound active device |
| GET /media/uploads/:mediaId | Read processing status | Reservation owner |
| POST /posts | Publish with one or more ready media IDs and optional caption | Authenticated author |
| GET /feed | Read published general Feed | Any authenticated account |
| GET /posts/:postId | Read one published post | Any authenticated account |
| GET /posts/mine | Read own publications | Authenticated author |
| GET /profiles/me/posts | Read own profile gallery | Authenticated author |
| PATCH /posts/:postId | Edit caption only | Author only |
| DELETE /posts/:postId | Delete own publication | Author only |
| GET /media/:mediaId | Authenticated original/preview delivery | Active session + published parent eligibility |

The profile gallery is an own-profile endpoint only in this proposal. Viewing another account's complete profile is not introduced. Nickname/avatar/profile fields must come from the existing privacy-safe profile projection; do not widen profile visibility.

## 5. DTO proposal

### Feed post

    {
      "postId": "opaque random identifier",
      "caption": null,
      "author": { "nickname": "Required displayed nickname" },
      "media": [
        {
          "mediaId": "opaque random identifier",
          "kind": "image",
          "renditions": {
            "thumbnail": "/media/opaque-id?variant=thumbnail",
            "display": "/media/opaque-id?variant=display"
          }
        }
      ],
      "createdAt": "server timestamp",
      "updatedAt": "server timestamp",
      "revision": 1,
      "isMine": false
    }

The paths above are authenticated API paths, not public URLs. The client must attach its current session credentials. DTO MUST NOT contain internal user IDs, email, phone, provider details, device/session IDs, security hints, private organization membership or raw object keys.

### Upload intent

    {
      "kind": "image",
      "sizeBytes": 123456,
      "sha256": "64 lowercase hex characters",
      "idempotencyKey": "opaque client-generated retry key"
    }

The declared kind/size/hash are validated against actual bytes and are not trusted. Server returns an opaque media ID, expiry and upload instructions; no permanent object URL.

### Publish request

    {
      "idempotencyKey": "opaque client-generated retry key",
      "caption": null,
      "mediaIds": ["opaque-media-id-1", "opaque-media-id-2"]
    }

Caption may be absent, null or normalized non-empty text. Empty/whitespace caption becomes null. Empty mediaIds is always rejected.

## 6. Pagination and cursor integrity

- Default page size 20; proposed maximum 50 pending load testing.
- Stable order: createdAt DESC, postId DESC.
- Database query uses keyset pagination with a matching composite index; never OFFSET.
- Cursor payload includes version, sort boundary and query scope. Cursor is authenticated with HMAC-SHA-256 using a server-held secret of at least 256 bits; use constant-time signature comparison and key-version support for rotation.
- Invalid, malformed, expired-version or tampered cursor returns 400 invalid_cursor.
- Cursor is not an authorization credential. Every request revalidates session and query scope.
- Snapshot semantics for inserts/deletes must be documented; tie-breaker prevents same-timestamp ambiguity. Do not claim absolute no-skip/no-repeat under arbitrary concurrent deletes without defining the traversal snapshot.

## 7. Ownership and mutation rules

- Author identity is derived exclusively from the active session and immutable after publication.
- Only the author can edit caption or delete the post. Foreign object mutations return a non-enumerating 404.
- Media order changes, if supported, must be author-only and revision-checked. Beta 1.0 minimum can keep media order immutable after publish.
- Optimistic concurrency uses expectedRevision; stale writes return 409 revision_conflict.
- Same author + same idempotency key + same canonical request returns the original result; same key + different request returns 409 idempotency_conflict.
- No client-supplied authorId, userId, deviceId, createdAt, status or object key is accepted.

## 8. Limits requiring technical calibration (not yet owner-approved)

Do not hard-code arbitrary limits. Before implementation, benchmark supported Android/iOS devices, API memory/streaming behavior, worker CPU/memory, storage and expected network conditions. Produce a documented proposal for:
- maximum photos per post;
- maximum video duration and resolution;
- maximum bytes per photo/video and total post;
- supported image/video codecs and containers;
- thumbnail/display rendition dimensions and quality;
- upload timeout, processing timeout, retry window and orphan retention;
- per-account upload/publish rate limits.

Safe engineering baseline: enforce finite configurable limits from the first implementation, reject unknown/unsupported formats, stream uploads instead of buffering whole files, bound worker concurrency and decompression resources, and never silently transcode beyond declared server policy. Exact numeric values remain an implementation gate pending evidence/owner approval.

## 9. Persistence and integration boundaries

- Add Feed-specific tables for posts, media, post-media association, upload reservations and cleanup outbox.
- Preserve PostgreSQL/in-memory behavioral parity where both stores are supported.
- Use foreign keys, uniqueness constraints, status checks and indexes for author/time, global Feed order, post/media order, upload expiry and cleanup retries.
- No schema/table/route changes are made until PR #171/#173 shared-file integration state is reconciled.
- Feed media uses a separate storage adapter/namespace and worker. Do not repurpose or weaken current chat file routes, signed-download checks, room membership checks or MLS file pipeline.
- Existing /files API is not the Feed API and must not become cross-account-readable as a side effect.

## 10. Security and acceptance matrix

| Scenario | Expected result |
|---|---|
| Anonymous or expired session reads Feed/post/media | 401 |
| Any active registered account reads a published Feed post | 200 |
| Any active registered account reads published Feed media | 200 after fresh session + parent eligibility check |
| Device revoked after a prior media request | Next media request denied |
| Author creates post with no media IDs | 400/422; no post row |
| Author references another user's media | 404/403; no post row |
| Author references pending/rejected/expired media | 409/422; no post row |
| Foreign account edits/deletes post | 404 |
| Client substitutes media ID/post ID | Object-level association and session checks deny unauthorized operation |
| Upload replay or conflicting idempotency key | Original response or 409; no duplicate object association |
| Declared MIME/extension differs from file bytes | Reject/quarantine; never publish |
| Malformed/truncated/oversized/decompression-bomb media | Reject within bounded resource budget |
| Cursor signature modified | 400 |
| Post deleted while media request starts | No new delivery after deletion state commits |
| DTO inspection | No email, phone, internal user/device/session IDs or private profile fields |
| Chat/MLS file regression | Existing behavior unchanged; Feed path isolated |

Dynamic security tests are mandatory. Static review alone is not acceptance.

## 11. Explicit exclusions

- Text-only publications.
- Anonymous/public web Feed.
- Public profile or changes to privacy variant В.
- Follow/block/subscription/social graph.
- Comments, reactions, shares and ranking unless separately approved.
- Stories, scheduled posts and drafts in the first public slice.
- Any change to chat MLS encryption, membership, chat file upload/download or existing room authorization.
