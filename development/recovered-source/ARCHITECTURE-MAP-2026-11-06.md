## 3. Сервер

- Точка входа: `src/main.js` (запуск `node src/main.js`), миграции: `node src/migrate.js`.
- Конфигурация: `src/config.js` (переменные окружения), флаги среды: `src/flags.js` (хранятся в базе, таблица `feature_flags`).
- Тестовый интерфейс: раздаётся только при `INONE_TEST_UI=1`; в продакшене режим запрещён проверкой конфигурации.
- Маршруты: 57 обработчиков с точным путём и 43 с регулярным выражением (всего вариантов 112 при сверке с кодом, см. `tools/verify_screens.py`).
- Группы маршрутов: аутентификация (`/register*`, `/login`, `/token/refresh`, `/logout`, `/auth/*`), восстановление (`/recovery/*`, `/admission/cancel`), шаги подтверждения (`/stepup/*`), аккаунт (`/account/*`, `/pin/*`, `/profile`), устройства (`/devices*`, `/approvals*`), комнаты (`/rooms*`, `/invites*`), MLS (`/mls/*`, `/keys/*`), события и сигналы (`/sync`), файлы (`/files*`, `/objects*`), организации (`/orgs*`, `/org-requests*`), администрирование (`/platform*`), конфигурация (`/config*`), поиск (`/users/search`).
- Правила доступа: участник комнаты должен быть участником одобренной организации комнаты (`room-permissions.js`, `org-*`); связи между организациями закрыты по умолчанию.
- Ограничение частоты: `src/rate-limit.js`, константы `DEFAULT_RATE_LIMITS`. Параметр `rateLimits` в `createServer` переопределяет их (используется только тестовым стендом).
- Новые аккаунты не входят в организацию по умолчанию (решение владельца); старые сохраняют членство (миграция 0020).

## 4. База данных

- 51 таблица. Группы таблиц: аккаунты и устройства (`accounts`, `devices`, `device_keys`, `device_signing_keys`, `device_waits`, `device_removals` через `mls_device_removals`), сессии и токены (`sessions`, `refresh_tokens`, `tokens`, `auth_tokens`), восстановление и вход (`recoveries`, `recovery_cancel_codes`, `approvals`, `login_throttle`, `email_codes`, `phones`, `pins`), комнаты (`rooms`, `room_members`, `room_events`, `room_assets`, `invites`, `join_requests`, `delivery_marks`), MLS (`mls_groups`, `mls_commits`, `mls_welcomes`, `mls_key_packages`, `mls_client_messages`, `mls_device_removals`), файлы (`files`), организации (`organizations`, `org_members`, `org_requests`, `org_request_documents`, `org_settings`, `org_links`, `org_request_log`, `org_settings_log`, `admin_action_log`, `platform_roles`), прочее (`feature_flags`, `flag_changes`, `rate_limits`, `push_tokens`, `inbox`, `sends`, `counters`, `profiles`, `provider_links`, `backup_emails`).
- Транзакций между состоянием группы и таблицами обработки на клиенте нет (см. раздел 10).

## 5. MLS и криптография

- Протокол: MLS по RFC 9420. Клиентский профиль: `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. Задан в ядре (`CIPHERSUITE`) и в эталонном клиенте ts-mls (`test/mls-reference-client.mjs`). Сервер профиль не проверяет.
- Ядро: OpenMLS 0.8.3, `max_past_epochs` = 16, идентификатор участника в учётных данных — `пользователь/устройство`, групповой состав — по устройствам.
- Сервер хранит шифротекст, коммиты и приветствия. Сервер не расшифровывает содержимое и не проверяет криптографию коммитов.
- Локальная база клиента: SQLCipher (`rusqlite` с `bundled-sqlcipher-vendored-openssl`), ключ передаёт платформа через интерфейс `KeyStore`. Реальных адаптеров iOS Keychain и Android Keystore в поставке нет.
- Megolm: адаптер `src/crypto-engine.js` поверх `@matrix-org/matrix-sdk-crypto-wasm` (версия 18.9.0) — это зависимость времени выполнения (`dependencies`). Адаптер импортируется тестовым клиентом `src/client.js`, который лежит в `src/`. Сервер принимает события `m.room.encrypted` в `/rooms/:id/events`. Это противоречит решению об исключении Megolm из продуктового пути (P0.6 не выполнен).
- Сверка состава (клиент): после каждой синхронизации состав группы по протоколу сравнивается с составом на сервере; расхождение приостанавливает отправку в комнату.
- Состояние RecoveryRequired: ошибка состояния одной комнаты (например, недопустимый коммит) приостанавливает отправку в неё, остальные комнаты синхронизируются. Автоматического восстановления нет.

## 6. Клиенты

- Ядро mls-client (Rust): `connect`, `create_room`, `invite`, `send_text`, `enqueue_text`, `flush_outbox`, `sync`, `take_incoming`, `undecryptable`, `desync_reason`, `revoke_device`, `remove_revoked_devices`, `local_epoch`, `members_of`.
- Классификация ошибок обработки (`classify_process_error`): временные ошибки (StorageError, LibraryError) повторяются позже; постоянные помечают событие и пишут причину в `client_undecryptable`.
- Очередь отправки: таблица `client_outbox`; повтор не создаёт дубликатов (`clientMessageId`).
- Мост: `OnceLock<Mutex<World>>` — глобальное состояние; продуктового Flutter-моста нет.
- Веб-экраны (0.7): общий слой `client-screens/common/api.mjs` (ошибки по `code`, токен только в памяти), идентификатор устройства в localStorage только в `common/device.mjs` (решение D6), экраны входа и регистрации в `client-screens/auth/`.

## 7. Тесты

- Node (движок): 85 файлов. Все входят в `npm test` (память и PostgreSQL) или `npm run test:db` (база). Итог TAP-отчёта `node --test` включает вложенные подтесты, поэтому числа 389 и 392 (сумма объявлений верхнего уровня) не равны.
- Rust: 9 интеграционных файлов плюс модульные тесты в `src/lib.rs`. Тестовый стенд: `tests/engine/start-engine.mjs` с командами FLAG, ADD_MEMBER, REMOVE_MEMBER, HIDE, SHOW, CORRUPT, BADB64, BADCOMMIT (только для тестов).
- Журнал поломок: `DELIBERATE_BREAKS.md` (24 раздела в a7f60b6). Каждое новое правило проверяется поломкой с возвратом файла побайтно.
- Тест-стратегия: интеграционные тесты против настоящего движка, разные наборы для памяти и PostgreSQL.

## 10. Известные технические ограничения

1. Megolm присутствует в продукте: зависимость времени выполнения, адаптер в `src/`, приём `m.room.encrypted` на сервере (P0.6).
2. Нет атомарности между состоянием группы (отдельное соединение SQLite у OpenMLS) и таблицами обработки. Сбой между применением коммита и записью маркера возможен (P0.2).
3. Сервер не проверяет профиль MLS (набор шифров, расширения, сериализация). Межреализационных (ts-mls и OpenMLS) тестов нет (P0.7).
4. Недопустимый коммит переводит комнату в RecoveryRequired, автоматического восстановления нет.
5. Событие с эпохой впереди текущей (без коммита) остаётся в очереди без явного сигнала (P0.4).
6. Ключи Keychain и Keystore не реализованы; есть только интерфейс KeyStore (P0.8).
7. Мост `mls-bridge` держит глобальное состояние; Flutter-мост не поставлен (P1.3).
8. Файлы: нет клиентского шифрования вложений и докачки (P1.4).
9. Отправитель push (FCM/APNs) не подключён.
10. Лимиты регистрации и других действий — константы в коде, а не флаги (`rate-limit.js`).
11. Тестовый клиент Node и тестовые экраны не являются продуктом; нужно изолировать их от продуктовой сборки.
12. Dart-код организаций (`client-reference/dart`) не проверен: нет Dart SDK.
13. Интерфейс подтверждения входа с нового устройства в продукте не реализован (экран 0.7.4, PR-07).
14. Производительность больших групп не измерена (500 и 1000 участников).

## 11. Расхождения, которые надо закрыть до публикации

1. Два источника кода: рабочая копия без git и публикационный репозиторий с git. Нужен один источник истины (предложение: git-репозиторий).
2. Отсутствие общего коммита с `main` (`1a40026`): история публикационного репозитория начинается с `694e140`. Полная история bundle не содержит коммитов `main`. Слияние возможно двумя путями, решение за CTO: отдельная ветка без изменения `main` или перенос файлов поверх `main` новым коммитом.
3. `SECURITY.md` есть только в публикационной копии, в рабочей копии его нет.
4. `DEVELOPMENT_REGISTER.md` и `CHANGELOG.md` не описывают волны 1–4 (записаны только в P0-WAVE-*.md и журнале поломок).
5. Документ архитектурных требований использует прежнюю нумерацию P0 в тексте волн; новая нумерация (см. ответ аудитору) в файле не отражена.
6. Результаты тестов в отчётах смешивают TAP-итоги и объявления; нужна одна метрика.
