# Исследование 0.7.0a: шифрование в браузере для экранов чата и групп

Статус: исследование выполнено по работам, ждёт решения владельца.
Дата: 5 ноября 2026. Автор: CTO (Claude).

## Вопрос
Каким клиентом шифрования пользоваться в браузере, чтобы экраны чата и групп (этапы 0.7.3 и 0.7.5) показывали и отправляли настоящие зашифрованные сообщения.

## Что установлено по коду и документам (факты)
1. Движок принимает два вида шифрованного трафика:
   - личные и групповые сообщения по MLS: маршруты /mls/groups/:id/commits, /mls/groups/:id/messages, /mls/welcomes, /mls/key-packages;
   - события комнаты: POST /rooms/:id/events принимает только тип m.room.encrypted (src/server.js).
2. Целевой путь по документам проекта (REMAINING_WORK.md): групповое и личное шифрование — MLS (RFC 9420). Megolm отменён. Эксперимент на ts-mls проходит. Кандидат для мобильной библиотеки — OpenMLS через FFI.
3. Текущий код: src/crypto-engine.js — временный адаптер к matrix-sdk-crypto-wasm (вариант A, решение заказчика). Адаптер помечен как временный: его заменит собственный движок (вариант B) после обкатки в бете Propo.
4. Тестовый клиент src/client.js шифрует содержимое сообщения через адаптер варианта A и отправляет его по MLS-маршрутам. Это смешанный путь. Для экранов его нельзя брать как образец: его надо разделить до этапа 0.7.3.
5. Ядро клиента на Rust (mobile-mls/mls-client): openmls 0.8, openmls_rust_crypto 0.5, хранилище на SQLite (openmls_sqlite_storage), блокирующий HTTP (ureq 2). Для браузера эти части не подходят без замены.
6. В среде установлен Rust только для x86_64 (rustlib: x86_64-unknown-linux-gnu). Сборки для wasm32 нет и без rustup её не поставить. Значит, путь 1 здесь проверить нельзя.
7. ts-mls версии 1.6.4 доступен в npm, лицензия MIT. Уже используется в test/mls-reference-client.mjs. Тесты контракта MLS проходят с ним.

## Пути
Путь 1. Ядро Rust собрать в WASM.
  Плюсы: одна реализация для продукта и браузера.
  Минусы: сборки wasm32 здесь нет; нужно заменить SQLite-хранилище и блокирующий HTTP; объём большой; здесь не проверяется.
  Оценка: несколько этапов.
  Вывод: не для 0.7. Кандидат для 0.8, если выберем Rust-ядро для продуктового клиента.

Путь 2. MLS на JavaScript (ts-mls) в браузере.
  Плюсы: MIT; уже совпадает с контрактом сервера в тестах; быстро проверяется здесь.
  Минусы: зрелость и аудит реализации; хранение ключей MLS в браузере (нужно решение); скорость при 500 и более участниках не замерена.
  Оценка: средний объём.
  Вывод: рекомендуется для тестовых экранов 0.7.3 и 0.7.5.

Путь 3. Адаптер варианта A (matrix-sdk-crypto-wasm) в браузере.
  Плюсы: готовый WASM-пакет, тот же, что в Element.
  Минусы: Megolm отменён как целевой путь; вариант A временный; групповые сообщения идут по MLS-маршрутам, а не по Megolm.
  Вывод: для новых экранов не рекомендуется. Запасной вариант только для личных чатов, если путь 2 не пройдёт.

## Рекомендация CTO
- Для тестовых экранов 0.7.3 и 0.7.5: путь 2 (ts-mls в браузере).
- Для продукта (0.8): оценить путь 1 отдельно, вместе с выбором мобильной библиотеки.
- Путь 3 не использовать для новых экранов. Смешанный путь в src/client.js разделить.

## Открытые вопросы для владельца
1. Хранение ключей MLS в браузере для тестовых экранов: только в памяти вкладки (просто, после перезагрузки вход заново) или в IndexedDB с шифрованием PIN (сложнее).
2. Разрешить путь 2 для тестовых экранов.
3. Замер скорости ts-mls при 500 и более участниках: провести в этапе 0.7.5.
